# DevFlow Clean Code（第三层）

## 总览

前两层保证代码做对的事、被证明做对；这一层保证代码本身写得好。判断标准只有一个视角：**下一个读者**（评审者、半年后的维护者、也包括下一轮迭代的 AI）。代码是写给人读的，顺便能在机器上运行。

人能持续低成本地审查 AI 的产出（human-on-the-loop 能成立），靠的就是这一层。所以"整洁"不是美学偏好，是协作姿态的前提。

本文是语言无关的标准；TDD implementer 的 REFACTOR 证据与 `clean_code_check` 以本文为通用基准。语言细则在对应的 `<language>-coding-standards` 技能（现有 `c-coding-standards` / `cpp-coding-standards`，可按同一契约扩展），它们叠加在本文之上而不是替代本文。示例用 C/C++ 写，原则通用。

## 五个维度与决策透镜

"整洁"不是单一标准，而是让同一份代码同时具备五个可被检验的属性——**简洁、可靠、可维护、可测试、高效**。本技能后面的每个机制小节（命名、函数、错误处理……）都是为某一个或几个维度服务的具体手段；维度是目的，手段是落点。

这张透镜是**写代码（REFACTOR 自检）和评审（R3）共用的入口**：写时按维度顺序取舍，审时按维度顺序提问。读完透镜就知道该翻到哪一节、该问哪个问题。

| 维度 | 没有它会怎样（要防的失败） | 写/审时的决定性一问 | 本技能落点 |
|---|---|---|---|
| **简洁** Simple | 读者要在噪音里找信号；改之前先得猜它在干嘛 | 能用更少的概念/分支/参数表达同一件事吗？ | §命名 §函数 §控制流 §注释 |
| **可靠** Reliable | 正常路径能跑，边界与失败路径悄悄崩或留下脏状态 | 每个失败和边界都有确定的、符合契约的去向吗？ | §错误处理写法 §控制流（卫语句/不变量） |
| **可维护** Maintainable | 改一处炸三处；新增一种情况要改 N 个地方 | 一个"变化理由"是否只落在一个地方？ | §SOLID §重复与死代码 §范围与提交纪律 §常见异味与重构手法 |
| **可测试** Testable | 必须 mock 内部、或依赖真实时钟/全局状态才能测 | 不碰真实边界，就能对这段逻辑写出确定断言吗？ | §为可测试性而写 |
| **高效** Efficient | 热路径里有白做的功；或为臆想的"快"牺牲了可读 | 这里的开销，是测出来的还是猜出来的？ | §性能纪律 |

把这五维做到位，**可演进性与可审查性会随之而来**——它们是整洁的回报，不是需要另外堆叠的指标（human-on-the-loop 能成立，正是靠这份回报）。因此本技能的取向继承 Robert C. Martin 的核心立场：**代码首先写给人读**；可靠靠让失败路径无处藏身，可测试靠把决策逻辑与副作用分离，高效靠"先正确清晰、再按测量优化"，而不是反过来用复杂度换取臆想的性能。

维度的优先级不是平均的：当维度冲突时，**可靠 > 简洁/可测试 > 可维护 > 高效**（牺牲可靠性换性能永远不可接受；牺牲可读性换未经测量的性能按 important 处理）。下面每个机制小节末尾标注它主要服务的维度。

## 命名

名字是最廉价的文档。规则：

| 对象 | 规则 | 反例 → 正例 |
|---|---|---|
| 函数 | 动词开头，说出做什么或返回什么 | `process()` → `discard_expired_sessions()` |
| 布尔 | is/has/can/should 开头，肯定语义 | `flag`, `not_ready` → `is_calibrated`, `has_pending_request` |
| 变量 | 名词，带足语义；作用域越大名字越长 | `d`, `tmp2` → `retry_delay_ms`, `merged_config` |
| 常量 | 说出含义而非值 | `TIMEOUT_3S` → `HANDSHAKE_TIMEOUT`（值变了名字不会说谎） |
| 带单位/语义的量 | 单位进名字或进类型 | `timeout` → `timeout_ms`；更好：`duration_ms_t timeout` |

判据：

- **名字撒谎是最高优先级的修复**：`get_config()` 里偷偷做了网络请求和缓存写入，比没有名字更糟。函数做的事超出名字 → 改名或拆函数。
- 同一概念全库一个词：别让 `fetch`/`load`/`read` 混用指同一件事。
- 名字里出现 `data`、`info`、`manager`、`util`、`process`、`handle` 而无修饰 → 几乎总能更具体。
- 需要注释解释名字含义 → 直接把解释写进名字。

> 维度：简洁（名字是最廉价的文档）；同一概念一个词同时服务可维护。

## 函数

- **一个函数一件事，一层抽象**。函数体内不应同时出现"调用其他函数表达意图"和"操作位与指针的细节"两个层次——细节下沉成命名函数。
- 经验阈值（超出即审视，不是机械红线）：函数 ≤ 50 行；参数 ≤ 4 个；嵌套 ≤ 3 层。
- 参数结伴出现（同一组 3-4 个参数在多个签名里重复）→ 提取结构体。
- 输出参数能用返回值就用返回值；布尔参数改变函数行为（`render(true)`）→ 拆成两个名字明确的函数。

**怎么拆长函数**：找出函数里的"段落"（通常已有空行或注释分隔），每个段落提取为一个以意图命名的函数。注释 `// validate input` + 十行代码 → `validate_input()`，注释删掉。

```c
/* ❌ 三个抽象层次挤在一起 */
int config_apply(const uint8_t *blob, size_t len) {
    if (blob == NULL || len < 8) return ERR_INVALID_ARG;
    uint32_t crc = 0xFFFFFFFF;                      /* 细节：CRC 计算 */
    for (size_t i = 0; i < len - 4; i++) { crc = crc32_step(crc, blob[i]); }
    if (crc != read_le32(blob + len - 4)) return ERR_CRC;
    ...30 行解析字段...
    ...20 行逐项生效与回滚...
}

/* ✅ 每层一个函数，主函数读起来就是流程本身 */
int config_apply(const uint8_t *blob, size_t len) {
    int rc = config_verify_integrity(blob, len);
    if (rc != OK) return rc;

    parsed_config_t parsed;
    rc = config_parse(blob, len, &parsed);
    if (rc != OK) return rc;

    return config_commit(&parsed);
}
```

> 维度：简洁 + 可维护；小而单一职责的函数同时让单元更易测（可测试）。

## 控制流

让主路径（happy path）保持在最低缩进层级，异常分支尽早离开：

```c
/* ❌ 主逻辑埋在三层嵌套里 */
int session_send(session_t *s, const msg_t *m) {
    if (s != NULL) {
        if (s->state == SESSION_OPEN) {
            if (msg_is_valid(m)) {
                /* 真正的发送逻辑，缩进三层 */
            } else { return ERR_INVALID_ARG; }
        } else { return ERR_BAD_STATE; }
    } else { return ERR_INVALID_ARG; }
}

/* ✅ 卫语句：前置检查依次出场，主逻辑零缩进 */
int session_send(session_t *s, const msg_t *m) {
    if (s == NULL) return ERR_INVALID_ARG;
    if (s->state != SESSION_OPEN) return ERR_BAD_STATE;
    if (!msg_is_valid(m)) return ERR_INVALID_ARG;

    /* 真正的发送逻辑 */
}
```

- 条件复杂到需要思考 → 提取为命名的谓词函数或解释变量：`if (is_retryable(err) && attempts < MAX_RETRIES)`。
- 同一个标志变量控制后面多段逻辑的开关 → 通常应拆成两条直线路径。
- 魔法数字/字符串一律命名常量；`if (mode == 3)` 在评审中按 important 处理。

> 维度：简洁 + 可靠（让正常路径直白、失败路径无处藏身）。

## 错误处理写法

设计层定了错误模型（`devflow-design`），编码层的纪律：

- **检查每个可失败调用**。忽略返回值必须显式且有理由：`(void)log_write(...);  /* 日志失败不影响主路径 */`
- **错误处理不喧宾夺主**：用卫语句/早返回让错误路径短促清晰，主路径保持直线。
- **失败时资源必须回收**。C 的多资源获取用集中清理出口（goto cleanup 模式，见 `c-coding-standards`）；C++ 用 RAII（见 `cpp-coding-standards`）。
- **不吞错误**：捕获/拦截了错误就必须处理（恢复、降级、上报）之一；空的 catch / 只打日志然后当没发生，按 critical 处理。
- 错误信息带上下文：报「config block 3 CRC mismatch (got 0x1A2B, want 0x3C4D)」而不是「verify failed」。

> 维度：可靠。卫语句与早返回同时服务简洁。

## 为可测试性而写

`devflow-tdd` 负责"写测试"，本节负责让代码**生来就能被测**。难测往往不是测试的问题，是代码的问题：测试难写 = 设计难用。编码时就消除下面这些"不可测结构"，而不是留给写测试时去 mock 绕开。

- **决策逻辑与副作用分离**：把"算什么"（纯函数：输入→输出，无 I/O、无全局、无时钟/随机）与"做什么"（读写硬件、文件、网络、时间）分开。纯逻辑能用普通断言直接测，无需任何 mock。
- **隐藏依赖外置**：时间、随机数、全局可变状态、单例是测试的头号敌人——它们让结果不确定、用例互相耦合。把 `now_ms()`、随机源、配置作为参数/注入点传入（与 §SOLID 的 DIP 同源），不要在函数体内直接抓全局。
- **只在真实边界留接缝**：需要 mock 的只能是真实边界（硬件、外部组件、慢依赖、时钟）。如果为了测一段内部纯逻辑而不得不 mock 模块内部，说明逻辑和副作用没分开——重构，而不是加 test-only 后门或给生产类塞测试专用方法。
- **可观察**：函数的效果要能从返回值或显式可查询的状态读到。把关键结果埋进无法观察的内部字段，等于把行为藏起来不让测。

```c
/* ❌ 决策逻辑里直接抓全局时钟，且只改内部状态——要测"过期判定"必须伪造系统时间 */
bool session_touch(session_t *s) {
    s->last_seen = sys_clock_ms();              /* 隐藏依赖：全局时钟 */
    if (sys_clock_ms() - s->created > s->ttl) { /* 决策和副作用缠在一起 */
        s->state = SESSION_EXPIRED;             /* 效果只落在内部字段 */
        return true;
    }
    return false;
}

/* ✅ 纯判定抽出来：给定时间就有确定答案，普通断言即可覆盖全部边界 */
bool session_is_expired(const session_t *s, uint32_t now_ms) {
    return now_ms - s->created > s->ttl;
}
/* 副作用留在薄薄的外层，由调用方把真实时钟传进来（真实边界注入） */
bool session_touch(session_t *s, uint32_t now_ms) {
    s->last_seen = now_ms;
    if (session_is_expired(s, now_ms)) { s->state = SESSION_EXPIRED; return true; }
    return false;
}
```

> 维度：可测试。分离副作用同时改善可靠（边界可枚举）与可维护（纯逻辑可复用）。

## 性能纪律：先正确清晰，再按测量优化

立场继承 Martin：**清晰优先，不做过早优化**。但"不过早优化"不等于"放任浪费"。两条纪律一起成立：

- **不牺牲可读性换未经测量的性能**：任何让代码更难懂的优化，必须有 profile / 基准数据撑腰，并在注释里写明"测出来快了多少、代价是什么"。说不出数据的"我觉得这样快" = 过早优化，按 important 处理。
- **不容忍无谓浪费**：与可读性无关、纯属"白做功"的开销该消除——循环里重复计算的不变量提到循环外、热路径上不必要的内存分配/拷贝/重复查找、明显能用线性解法却写成 O(n²) 的内层扫描。这类不是"优化"，是把本就该清晰的代码写对。
- **知道热路径在哪**：优化只对测量证明的瓶颈做，且尽量局部化（封装在命名良好的函数里，不让复杂度渗进主流程）。设计层的算法复杂度/资源预算约束见 `devflow-design`；实时性、内存、中断时延等领域约束见 `embedded-development`。

```c
/* ❌ 把不变量和昂贵调用塞进循环条件，既慢又把意图埋了 */
for (size_t i = 0; i < strlen(s); i++) {        /* 每轮都重算长度：O(n²) */
    buf[i] = to_upper(s[i]);
}

/* ✅ 不变量提到循环外：更快，也更直说意图。无需任何"技巧" */
size_t n = strlen(s);
for (size_t i = 0; i < n; i++) {
    buf[i] = to_upper(s[i]);
}
```

> 维度：高效。它从不凌驾于可靠之上，也不能以牺牲可读性为默认代价。

## 注释

注释解释**为什么**，代码说明**是什么**。

```c
/* ❌ 复述代码 */
i++;  /* i 加一 */

/* ✅ 解释代码说不出的约束、取舍、外部事实 */
/* 先写数据后写索引：掉电时宁可丢这条记录，不可指向垃圾数据 */
record_write(slot, &data);
index_update(slot);
```

值得写注释的场景：非显然的不变量与前置条件、为绕过硬件/第三方缺陷的奇怪写法（带 issue 链接）、有意为之的"看似低效"、并发约束（"只能在任务上下文调用"）。

不写的：版本历史（git 的事）、注释掉的代码（删，git 里有）、段落标题式注释（提取函数代替）、TODO 不带负责人和去向（要么登记成债务，要么删）。

> 维度：简洁（代码自解释）；解释 why 的注释保住可维护。

## 重复与死代码

- **三次法则**：第二次复制可以容忍（标记），第三次必须提取。但**只提取真正相同的知识**——两段代码长得像但服务不同业务规则、会因不同理由变化，提取反而制造耦合（错误的抽象比重复更贵）。
- 死代码零容忍：不可达分支、未使用变量/函数/参数、永远为真的条件、"以防万一"保留的旧实现——删。版本控制就是你的"以防万一"。
- 僵尸兼容层（`#if 0`、`legacy_` 前缀但无调用方、deprecated 但无下线计划）：登记并删除或给出下线计划。

> 维度：可维护（消除"改一处炸三处"）+ 简洁。

## SOLID 在编码时的落点

设计层负责判断边界，编码层负责让这些判断在 diff 里成立。看到 SOLID 问题时先找最小重构动作，不为原则本身制造新抽象：

| 原则 | 编码坏信号 | 小步动作 |
|---|---|---|
| SRP | 函数/文件同时处理解析、校验、持久化、通知等多个变化理由 | Extract Function / Move Function；必要时回 `devflow-design` 拆模块 |
| OCP | 新增一种类型要改多处条件分支 | 真实变化轴已确认时，用查表、策略或多态集中变化点 |
| LSP | 某个实现要求更强前置条件、返回不同错误语义或破坏失败状态保证 | 收紧契约或拆接口；不能替换就不要伪装成同一抽象 |
| ISP | 调用方 include 大头文件、传入无关配置、依赖内部字段 | 拆小 API / 参数结构；隐藏内部结构和私有宏 |
| DIP | 高层业务流程直接调用硬件、协议、存储或第三方库细节 | 在真实边界引入适配函数；单实现且无真实边界时保持具体依赖 |

> 维度：可维护（变化点集中）；DIP 在真实边界的接缝同时服务可测试。

## 范围与提交纪律

- **一个 diff 一个目的**：行为变更、重构、格式化分开提交。评审者无法在 500 行混合 diff 里分辨哪个变化是有意的。
- 只改任务要求改的。路过发现的问题：登记（issue / plan.md 债务登记节），不顺手修。
- **童子军规则的边界**：触碰范围内的小清理（改个错字命名、删几行死代码）值得做且随手做；超出触碰范围、或清理本身值得独立评审 → 登记。
- 不删不理解的代码、不"顺手统一"无关文件的风格。

## 常见异味与重构手法

完整目录（识别特征 + 操作步骤 + before/after）见 `references/refactoring-catalog.md`。速查：

| 异味 | 识别 | 手法 |
|---|---|---|
| 长函数 | 一屏放不下 / 多个段落注释 | Extract Function（按意图段落拆） |
| 深嵌套 | ≥3 层缩进 | 卫语句 / 提取谓词 / 反转条件 |
| 魔法数 | 裸字面量参与逻辑 | 命名常量（说含义不说值） |
| 数据泥团 | 参数组在多个签名重复 | 提取结构体 |
| 特性依恋 | 函数大量操作别的模块的数据 | Move Function 到数据所在地 |
| 霰弹式修改 | 一个行为变更要改 N 个文件 | 按变化理由重新聚合（回 `devflow-design`） |
| 开关参数 | 布尔参数改变函数行为 | 拆成两个函数 |
| 注释补丁 | 注释解释一段代码在干嘛 | 提取函数，注释变函数名 |
| 隐藏依赖（难测） | 函数体内直接读 `now()`/随机/全局可变状态 | 外置为参数或注入；决策逻辑抽成纯函数 |
| 循环内白做功（低效） | 不变量在循环里重复计算 / 多余分配拷贝 / 可避免的 O(n²) | 提到循环外 / 消除多余拷贝 / 换线性解法 |

重构永远在绿灯上进行、小步、每步跑测试（纪律见 `devflow-tdd` 的 REFACTOR 节）。

## 合理化反驳

| 话术 | 现实 |
|---|---|
| 「这个命名我自己懂」 | 代码是给下一个读者写的；"自己懂"的名字两周后你自己也不懂 |
| 「先跑起来，以后再清理」 | "以后"不存在。REFACTOR 是循环的一部分，不是可选附录 |
| 「多留个参数/分支，以后可能用」 | 死代码 + 假想需求。YAGNI；要用的时候再加，git 会帮你记住一切 |
| 「注释写多点总没错」 | 复述代码的注释会腐烂成谎言；该改的是代码的表达力 |
| 「顺手把旁边的也改了」 | 范围扩张让 diff 不可审。登记，另开任务 |
| 「这段复制一下改两行就行」 | 第三次复制时逻辑已经悄悄分叉。检查是不是同一个知识点 |
| 「这逻辑没法测，得 mock 一堆内部」 | 难测是设计信号：把决策逻辑从副作用/时钟/全局里拆出来，纯函数无需 mock |
| 「这样写更快」（说不出数据） | 没有 profile 的"更快"是过早优化。可读优先，瓶颈用测量证明后再局部优化 |
| 「这点性能损耗无所谓，先跑起来」 | 无谓浪费（循环内重复计算、多余拷贝）不是"优化项"，是该写对的代码 |

## 自检清单（提交前）

按五维度逐条自检，结论汇报进 `clean_code_check`——每维一句"过 / 不适用 + 具体理由"，不接受"看起来整洁"这类空结论：

- [ ] **简洁**：函数名说出全部行为、布尔肯定语义、量有单位；无函数 >50 行 / >4 参数 / >3 层嵌套而无登记理由；无裸魔法数；无注释掉的代码、未使用符号、复述型注释
- [ ] **可靠**：每个可失败调用被处理或显式注明忽略理由；失败路径资源回收、状态符合契约；主路径低缩进、异常早返回
- [ ] **可维护**：一个变化理由只落一处（无上帝函数 / 霰弹式修改）；第三次出现的相同知识已提取；diff 单一目的、范围内无未登记的顺手修改
- [ ] **可测试**：决策逻辑与副作用 / 时钟 / 全局状态分离；只在真实边界留 mock 接缝；无 test-only 后门；关键效果可从返回值或可查询状态观察
- [ ] **高效**：热路径无重复不变量计算 / 多余分配拷贝 / 可避免的 O(n²)；任何牺牲可读性的优化都有测量数据与注释，否则回退到清晰写法
- [ ] 适用语言的 `<language>-coding-standards` 细则已过
