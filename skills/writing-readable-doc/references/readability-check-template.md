# 可读性检查模板

本文提供三样东西：作者的冷读测试记录、`doc_readability_check` 返回模板、reviewer 的验收与 finding 写法。这些都是交接说明，不新增门禁，也不写进规范文档；`change.json` 的字段和状态不受本技能影响。

## 一、冷读测试记录

改写前做一次，改写后再做一次。做法：只拿这份文档和它显式引用的 canonical 章节，不看聊天记录、不看代码，回答五个问题。

```markdown
## 冷读测试（2026-09-03，delta-design.md）

| 问题 | 能否只凭文档回答 | 依据 | 判定 |
|---|---|---|---|
| 这次改什么 | 是 | DD-003/DD-007 的局部 before/after | 通过 |
| 为什么必须改 | 是 | DEF-1183 + FR-012 Source | 通过 |
| 什么保持不变 | 否 | DD-007 只写“保留其余语义”，未列出具体项 | 可读性缺陷 |
| 怎么算做对 | 是 | TC-014、TC-018 | 通过 |
| 风险在哪 | 否 | “必要时回滚”，无触发条件 | 内容缺陷 → devflow-design |
```

判定只有三种，不要含糊：

| 判定 | 条件 | 处理 |
|---|---|---|
| 通过 | 文档里能直接读到答案 | —— |
| 可读性缺陷 | 事实在文档里，但要翻代码、问作者或反复回读才能拼出来 | 本技能改写 |
| 歧义 | 能读出两个互相冲突的答案 | 按 `critical` 处理，先消歧再送审 |
| 内容缺陷 | 事实根本不在文档里 | 登记 Open Question / finding，回 `devflow-specify` 或 `devflow-design` |

## 二、doc_readability_check

请求 R1/R2 评审时随工件一起给出。

```markdown
doc_readability_check:
- 冷读: 五问中 4 项通过；“什么保持不变”不通过，已在 DD-007 补出保留项清单
- 结构: 3 个章节把结论提到首句；删除 2 段模板复读，改为带锚点的 N/A 理由
- 术语: “链路/连接/通道”统一为“会话（session）”，文档开头新增术语表
- 句式: 拆分 7 处长句；还原 12 处名词化；删除 9 句空转句
- 混排: 中英空格与全角标点统一；阈值补齐统计口径写法（P99 ≤ 50 ms 保持原值不变）
- 保义: 未触碰 EARS、Given/When/Then、QAS 五要素、DS/DD selector 与基线摘录；
        ID、数值单位、反引号内容三项集合改写前后一致；SHALL ×6、Given/When/Then ×18 计数不变；
        `ERR_CONFIG_INVALID` 出现次数 2 → 3，因为 §2 改成对照表时引用了 DD-007 已有的 after 内容
- 内容缺陷: 2 项已登记 —— NFR-003 缺重试阈值（devflow-specify，@需求负责人）；
        delta-design 6.2 缺回滚失败后的状态（devflow-design，@设计负责人）
```

填写规则：

- 每项写具体结论和数量，不写“已优化”“已检查”。
- `保义` 一项必须给出比对结果，不能只写“未改语义”。
- `内容缺陷` 为空时写 N/A 加理由，例如“全文无万能限定词，阈值均带单位与口径”。
- 没做改写时同样要给这份说明，说明冷读测试通过。

## 三、reviewer 验收

R1/R2 的 reviewer 可以按下列条件拒绝或降级：

| 情况 | 处理 |
|---|---|
| 缺 `doc_readability_check`，且文档冷读测试有不通过项 | 要求补齐后再审 |
| `doc_readability_check` 只有“已优化可读性”一类结论 | 视为未自检 |
| 改写批次里同时出现事实变化（阈值、ID、验收、契约） | 按未闭环处理，要求拆分 diff |
| 规范层被改写（EARS 变形、阈值消失、基线摘录不再逐字一致） | `critical`，回作者阶段回退并复审 |
| 模糊词被换成另一个模糊词，未登记内容缺陷 | `important`，回对应阶段补事实 |
| 只有措辞、连接词、空格问题 | `minor`，不阻塞门禁，但要有 Resolution |

reviewer 只读：在评审上下文里不改文档，只出 finding。

## 四、finding 写法

沿用 `devflow-review` 的 finding 结构：位置 + 问题 + 为什么有风险 + 严重级 + 分类 + 建议返工阶段 + 可执行方向 + Resolution 槽位。

```markdown
### F-03 delta-design.md 5.2 保留语义未列举

- 位置：`delta-design.md` 第 5.2 节，DD-007 的 preservation clause
- 问题：只写“其余语义保留”，没有列出被保留的错误码、并发约束和兼容窗口
- 风险：canonical sync 时无法判断哪些语义必须原样保留，容易在合并中静默丢失
- 严重级：important
- 分类：LLM-FIXABLE
- 返工阶段：devflow-design
- 方向：按 canonical `4.2 配置持久化` 的六项契约逐项列出保留项；只补表达，不改语义
- Resolution：<待作者回填>
```

```markdown
### F-05 srs.md NFR-003 阈值缺失（表达无法修复）

- 位置：`srs.md` NFR-003 的 Response Measure
- 问题：写作“必要时快速重试”，无次数、间隔、超时与统计口径
- 风险：QAS 不完整，测试 Case 无法从五要素推导，R1 不可判定
- 严重级：critical
- 分类：USER-INPUT
- 返工阶段：devflow-specify
- 方向：向需求负责人确认重试次数、间隔与超时上限及来源；不得用同义词改写掩盖
- Resolution：<待作者回填>
```

第二例说明本技能的边界：可读性 finding 指出“读不懂”，但当根因是缺事实时，去向是需求或设计阶段，而不是改写。

## 五、批量扫描

对整个 change 目录做一次机械扫描，找出高频问题的位置，再人工判断：

```bash
CHANGE=<component-root>/specs/changes/ARXXX-topic

# 万能限定词与空词（多为内容缺陷线索）
rg -n '通常|一般来说|原则上|必要时|尽可能|合理的|适当的|有效地|为了更好地' "$CHANGE"

# 名词化句式
rg -n '进行[^，。]{0,8}(处理|校验|操作|管理|优化)|实现对|完成对|具备[^，。]{0,6}的能力' "$CHANGE"

# AI 腔与无来源猜想
rg -n '综上所述|总的来说|不仅.*而且|未来可以|后续可考虑|充分考虑' "$CHANGE"

# 无锚点断言
rg -n '如上所述|见相关章节|参考前文|如设计所述' "$CHANGE"

# 中英之间缺空格（英文字母或数字紧贴中文）
rg -n '[\p{Han}][A-Za-z0-9]|[A-Za-z0-9][\p{Han}]' "$CHANGE"
```

扫描结果是线索不是判决：反引号内的代码、表格里的 ID、引用的基线摘录都会命中，必须逐条确认后再改。命中在规范层的，一律不改。
