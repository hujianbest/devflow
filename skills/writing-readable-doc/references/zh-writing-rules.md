# 中文工程写作细则

本文是 `writing-readable-doc` 的表达层细则，写初稿和改写既有文档时都适用。所有例子取自 DevFlow 文档的真实形态（`srs.md`、`delta-spec.md`、`delta-design.md`、`specs/spec.md`、`specs/design.md`）。改写时先确认目标句属于表达层，规范层的判定见 `rewrite-protocol.md`。

## 一、句子

### 1.1 长度与断句

一句话讲一件事。超过约 40 个中文字，或出现两个以上动作、两个以上条件时拆开。

```markdown
❌ 在设备重启后，如果检测到持久化区域中的配置版本低于当前固件所支持的最低版本，
   则需要执行迁移流程，并在迁移失败时回滚到出厂配置，同时上报一条告警事件。

✅ 设备重启时按以下顺序处理低版本配置：
   1. 配置版本低于固件支持的最低版本时，执行迁移。
   2. 迁移失败时回滚到出厂配置。
   3. 回滚后上报 `EVT_CONFIG_ROLLBACK`。
```

判断依据不是字数本身，是评审者能不能一次读完就复述出来。需要回读第二遍的句子就该拆。

### 1.2 主语与代词

跨句、跨段的 `其`、`该模块`、`这一机制`、`上述流程` 一律换成名字或 ID。同一句内指向唯一时可以保留。

```markdown
❌ 该组件在其初始化完成之前不应被调用，否则它的内部状态可能不一致。
✅ `config_store` 初始化完成前不得调用 `config_apply()`；未初始化时返回 `ERR_BAD_STATE`。
```

### 1.3 条件与例外

条件前置，动作后置，例外单独成句。不要把例外塞进主句的从句里。

```markdown
❌ 模块会在收到请求后进行处理，但在队列已满或设备处于休眠状态时除外。
✅ 收到请求后立即处理。两种情况不处理：队列已满时返回 `ERR_BUSY`；设备休眠时排队等唤醒。
```

### 1.4 否定改肯定

能写肯定就不写否定，双重否定一律改写。

```markdown
❌ 不允许在未完成校验的情况下不进行回滚。
✅ 校验未完成时必须回滚。
```

## 二、词汇

### 2.1 名词化还原

“对 X 进行 Y” 是最常见的 AI 中文句式，几乎总能还原成一个动词。

| 反例 | 正例 |
|---|---|
| 对配置数据进行校验 | 校验配置数据 |
| 对异常情况进行处理 | 处理异常 / 返回 `ERR_*` |
| 实现对超时的检测 | 检测超时 |
| 完成参数的初始化工作 | 初始化参数 |
| 具备容错的能力 | 可以容错 |
| 提供数据存储的支持 | 存储数据 |
| 做出相应的调整 | 改成 X（写清楚改成什么） |

### 2.2 空词黑名单

下列词删掉后语义不变，就删掉：

`为了更好地`、`有效地`、`充分地`、`相关的`、`一定程度上`、`整体而言`、`众所周知`、`值得注意的是`、`需要指出的是`、`不难看出`、`显而易见`、`进一步`、`持续优化`、`深度赋能`、`全面提升`、`强有力的保障`、`良好的`、`丰富的`

```markdown
❌ 为了更好地保障系统的稳定性，我们对相关的重试逻辑进行了进一步的优化。
✅ 重试次数从 3 次降到 1 次，避免弱网下打满连接池。
```

### 2.3 万能限定词

`通常`、`一般来说`、`原则上`、`必要时`、`尽可能`、`适当地`、`合理的` 修饰硬约束时是内容缺陷的信号，不要靠换词处理。

```markdown
❌ 必要时系统应当尽可能快地重试。
→ 登记 Open Question：重试触发条件是什么？最大重试次数？两次重试间隔？
✅（补齐来源后）连接超时后重试 2 次，间隔 200 ms；仍失败返回 `ERR_TIMEOUT`。
```

### 2.4 连接词节制

`此外`、`同时`、`然而`、`因此`、`不仅……而且……`、`不是……而是……` 连续出现是 AI 味的主要来源。段落顺序本身应表达逻辑，连接词只在转折真实存在时使用。

```markdown
❌ 此外，该方案还提升了可维护性。同时，它也降低了耦合。因此，我们推荐该方案。
✅ 推荐方案 A：它只改动 `config_store` 一个文件，方案 B 需要同时改动上层三个调用方。
```

### 2.5 “的”字串

一个名词短语最多留一个 `的`。

```markdown
❌ 用于在异常场景下的配置数据的恢复的流程
✅ 异常场景下的配置恢复流程
```

## 三、段落与结构

### 3.1 结论先行

段落第一句是判断，后面是证据。章节第一段是该章的结论，不是背景铺垫。

```markdown
❌ 配置模块最早在 2019 年引入，当时的需求是……。随着设备形态增加，出现了……。
   经过评估，我们认为……。因此本次变更决定保留上一份生效配置。
✅ 本次变更把配置加载失败的行为从“清空并继续”改为“保留上一份生效配置”。
   原行为会让设备在弱网重启后丢失标定参数（见 DEF-1183）。
```

### 3.2 段落长度

一段不超过 5 行。超过就找到段内的第二个判断，把它提成新段或列表项。

### 3.3 列表与表格

三项以上的并列，且各项有共同维度（触发条件、返回值、影响范围、owner）时用表格，每列一个维度。列表项不要写成“粗体词 + 冒号 + 复述”。

```markdown
❌ - **性能：** 性能得到了提升。
   - **可靠性：** 可靠性有所增强。
   - **可维护性：** 代码更易维护。

✅ | 维度 | 变化 | 证据 |
   |---|---|---|
   | 启动耗时 | 120 ms → 45 ms | TC-014 基准输出 |
   | 弱网重启保留标定 | 丢失 → 保留 | TC-018 |
```

表格里不要塞长句。单元格是取值、ID、阈值、一句结论；推导过程放表格外。

### 3.4 可定位

任何“如设计所述”“见相关章节”“参考上文”都要换成可跳转的锚点：稳定 ID、章节路径、文件名、行为编号。评审者要能立刻核对，而不是全文搜索。

```markdown
❌ 该行为在设计文档中已有说明。
✅ 见 `specs/design.md` 的 `4.2 配置持久化`，本次变更由 DD-007 局部修改。
```

### 3.5 不重复上下文

change 身份、`baseRevision`、profile、门禁状态只在 `change.json` 里有一份。文档正文不要复述，也不要每章重申一次目标。重复内容会和唯一真相不同步，制造第二处需要核对的地方。

## 四、中英混排与格式

| 项 | 规则 | 例子 |
|---|---|---|
| 中英之间 | 加一个半角空格 | `使用 CRC32 校验`、`调用 config_apply()` |
| 中文与数字 | 加一个半角空格 | `超时 50 ms`、`重试 2 次` |
| 标点 | 中文正文用全角 `，。；：（）【】` | 不写 `,` `.` `()` 混排 |
| 代码与标识符 | 反引号包裹，保持英文原形 | `` `ERR_CONFIG_INVALID` ``、`` `specs/spec.md` `` |
| 单位 | 数字与单位之间一个空格，单位用国际写法 | `50 ms`、`4 KB`、`100 Hz` |
| 比较与口径 | 写明比较符与统计口径 | `P99 ≤ 50 ms`、`峰值 ≤ 4 MB` |
| 引号 | 中文正文用中文引号 | 「」或 “”，不与英文引号混用 |
| 标题 | 名词短语，不写“关于……的说明” | `配置回滚流程`，不写 `关于配置回滚流程的说明` |
| 强调 | 每段最多一处加粗，且加粗的是判断不是名词 | 不要给每个条目开头加粗 |
| 表情符号 | 不使用 | —— |

## 五、术语表

术语漂移是中文技术文档最贵的可读性缺陷：评审者要先猜两个词是不是一个东西，才能判断语义。

规则：

1. 同一概念全文一个词。
2. 首次出现给中英对照：`会话（session）`。
3. 之后固定用中文或固定用英文，不交替。
4. 已固定的英文技术词不翻译：`callback`、`CRC`、`DMA`、`ACK`、`watchdog`。
5. 缩写首现给全称：`OTA（over-the-air 升级）`。

文档超过三个易混术语时，在文档开头加一张术语表：

```markdown
## 术语

| 术语 | 英文 | 定义 | 不要写成 |
|---|---|---|---|
| 会话 | session | 一次鉴权后建立、到显式关闭或超时为止的连接上下文 | 链路、连接、通道 |
| 生效配置 | active config | 当前正在被业务读取的那一份配置 | 当前配置、有效配置 |
```

`不要写成` 这一列直接给出被禁用的同义词，改写和评审都可以按它做机械检查。

## 六、常见 AI 中文句式与替换

| AI 句式 | 问题 | 改写方向 |
|---|---|---|
| `本方案在保证 X 的同时提升了 Y` | 不可证伪 | 给数字或行为差异 |
| `通过……的方式来……` | 翻译腔 + 名词化 | 直接写动作 |
| `基于……的考虑` | 隐藏真实理由 | 写出具体理由和来源 |
| `在……的情况下` | 冗长 | `……时` |
| `不仅……而且……` | 排比撑场 | 拆成两句陈述 |
| `综上所述，……` | 结论重复 | 删掉；结论已在开头 |
| `未来可以进一步扩展为……` | 无来源的猜想 | 删掉，或登记为 `EXC-xxx` |
| `该设计充分考虑了扩展性` | 无法审查 | 写清楚哪个扩展点、由哪条需求驱动 |
| `以确保系统的稳定运行` | 以 -ing 式收尾的空分析 | 删掉从句，或写出失败模式 |
| `相关模块会做出相应处理` | 主语与动作都模糊 | 写模块名与具体行为 |

## 七、改写自检

- [ ] 抽查五句，每句都能被评审者反驳
- [ ] 无句子需要回读第二遍
- [ ] 跨句代词全部落到名字或 ID
- [ ] 名词化短语已还原为动词
- [ ] 空词与万能限定词已删或已登记为内容缺陷
- [ ] 术语全文一致，首现有中英对照，必要时有术语表
- [ ] 三项以上并列已表格化，单元格里没有长句
- [ ] 中英空格、全角标点、单位与统计口径统一
- [ ] 没有“综上所述”式收尾段
