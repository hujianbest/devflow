# 可读的文档写作（中文）

## 总览

DevFlow 的门禁靠人。R1、R2 和 canonical diff 确认都要求人在有限时间内读懂文档并给出判断。文档读不懂，人就只剩两个选择：空过，或者整体打回。两种都让门禁失效，human-on-the-loop 退化成 human-rubber-stamping。

所以本技能的目标不是“文笔好”，是**可审查**：评审者只读文档，不看聊天记录、不翻代码，就能判断这次要改什么、为什么这样改、什么保持不变、怎么验证、风险在哪。

**本技能主要在写之前加载，不是写完之后补救。** 第一遍就按规则写，成本只是换个句式；写完再改，要受保义约束、要做集合比对、要拆成独立 diff，还要冒改坏规范内容的风险。文档已经写出来时也用本技能，但那是次优路径。

只有一条边界必须先立住：**规范层逐字不动，表达层可以改。** 阈值、稳定 ID、EARS 语句、Given/When/Then、QAS 五要素、delta 的基线摘录都是合并与验收的依据，一个字改错就破坏证据链。可读性工作永远只发生在表达层。

## 适用边界

本技能覆盖交付文档中的自然语言：`srs.md`、`delta-spec.md`、`delta-design.md`、`specs/spec.md`、`specs/design.md`、`tasks.md` 的说明性文字、`reviews/` 的 finding 叙述、`closeout.md`、`docs/learnings/` 的经验正文。

不覆盖：

- 代码、注释、标识符命名与测试命名 —— 那是 `devflow-clean-code` 和语言规范技能的范围。
- `change.json` 等结构化文件 —— 字段和状态由交付结构契约决定，不做措辞优化。
- 需求本身的正确性、完整性、可测试性 —— 那是 `devflow-specify` 和 `devflow-design` 的判断，本技能不替它们做决定。

写作语言是中文；代码标识符、协议名、错误码、路径、命令保持英文原形并放进反引号。

## 写初稿时

动笔前先做三件事，它们决定文档能不能被读懂，事后再补代价最大：

1. **定判断**：逐节写下这一节要让评审者得到哪个判断，把它当成该节第一句。写不出判断的章节，说明这节要么没内容，要么不该存在。
2. **定术语**：开写前固定每个概念的用词，一个概念一个词，首次出现给中英对照。术语漂移是评审者最贵的负担，事后统一还要逐处核对是否指同一对象。
3. **定规范片段的位置**：EARS Statement、Given/When/Then、QAS 五要素、阈值、稳定 ID、delta 的基线摘录与 selector，一律按模板原样写。它们一旦写下就属于规范层，之后任何人都不能为了通顺去动它们。

写的过程中守住这几条，其余细则见 `references/zh-writing-rules.md`：

- 每节第一句是判断，背景和推导放后面。
- 一句一事。写完一句就自问：评审者能对这句说“不对”吗？不能就删掉或换成事实。
- 动词优先，不写“对……进行……的处理”。
- 三项以上并列且维度相同，直接写表格，别写成长段。
- 中英之间空一格，数字带单位、比较符和统计口径。
- 不写“综上所述”式收尾段，结论已经在开头。
- 写不出阈值、来源或保留语义时，写成 Open Question 或可审查的 N/A 理由，不要用 `通常`、`必要时`、`合理的` 填空。

初稿阶段没有基线，不需要跑保义比对。**保义流程只在修改已存在的文字时适用**，见下面两节。

## 冷读测试

初稿写完先自测一次；改写既有文档时，先对原文做一次基线冷读，再对改写结果做一次。只给这份文档（外加它显式引用的 canonical 章节），不给聊天记录、不给代码，要求回答五个问题：

| 问题 | 通过标准 |
|---|---|
| 这次改什么 | 能列出可观察的行为差异，不是“优化了模块” |
| 为什么必须改 | 能指出来源（单据、缺陷、上游需求 ID），不是“为了提升质量” |
| 什么保持不变 | 能说出被保留的语义与兼容承诺 |
| 怎么算做对 | 能找到验收条件、阈值和对应 Case ID |
| 风险在哪 | 能说出触发条件、影响面和回滚动作 |

判定规则决定后续走向，不要混为一谈：

- 某一问必须靠翻代码或问作者才能回答 → **可读性缺陷**，用本技能改写。
- 某一问在文档里能读出两个互相冲突的答案 → **歧义**，按 critical 处理，先消歧再送审。
- 某一问的事实文档里根本没有 → **内容缺陷**，回 `devflow-specify` 或 `devflow-design` 补，写成 Open Question 或 finding，禁止靠润色把缺口写圆。

## 保义改写红线

修改已有文字前，先把文档切成两层。下列内容**逐字不动**；写初稿时，这份清单同样告诉你哪些片段必须按模板写、写完就不再润色：

- 稳定 ID 与其编号：`FR-xxx`、`IFR-xxx`、`NFR-xxx`、`CON-xxx`、`ASM-xxx`、`EXC-xxx`、`DS-xxx`、`DD-xxx`、`DEC-xxx`、`TC-xxx`、canonical 章节路径与实体键。
- EARS 语句的关键词与结构（`WHEN` / `WHILE` / `IF` / `WHERE` / `THE` / `SHALL`）。
- Given/When/Then 验收的条件与预期。
- QAS 五要素（Stimulus Source、Stimulus、Environment、Response、Response Measure）及其数字、单位、比较符、统计口径。
- delta operation 的 target、selector、基线摘录与 digest、局部 before/after、preservation clause。
- 接口签名、字段名、错误码、路径、命令、反引号内的一切内容。
- 追溯表的列结构与锚点。
- canonical 章节标题：它是稳定显示名，改动只能走 delta 的 `RENAMED` 操作，不算润色。

可改的是这些：章节导语、背景与理由叙述、影响与风险描述、方案说明、决策比较的正文、非规范注解、条目之间的过渡。

```markdown
❌ 把规范层“润色”掉
- 原文：WHEN 收到 SetConfig 请求 THE 配置模块 SHALL 在 50 ms 内返回结果。
- 改写：配置模块会尽快响应 SetConfig 请求。
  （EARS 结构没了，50 ms 阈值没了，这条需求不再可测）

✅ 规范层原样保留，只改周围的说明
- WHEN 收到 SetConfig 请求 THE 配置模块 SHALL 在 50 ms 内返回结果。
- 说明：50 ms 来自 AR-217 的下发链路预算，写入线程占 30 ms，回执占 20 ms。
```

改写后自检，确认动的只有表达层：

```bash
git diff --word-diff -- <doc>
rg -o '\b(FR|IFR|NFR|CON|ASM|EXC|DS|DD|DEC|TC)-[0-9]+' <doc> | sort -u          # 集合一致
rg -o '[0-9]+(\.[0-9]+)?\s*(ms|s|us|MB|KB|%|次|条|Hz)' <doc> | tr -d ' ' | sort -u  # 集合一致
rg -c 'SHALL|Given|When|Then' <doc>                                             # 计数不变
```

集合是硬条件：不新增、不丢失。出现次数可以变化（拆句、改表格会重复引用同一个 ID 或错误码），但次数变化必须写进改写记录；次数减少要逐处说明删掉的是哪句表达层文字。数字比较前先去掉空格，否则 `50ms` 改成 `50 ms` 会误报。

集合对不上就回退这次改写，不要在解释里辩护。

## 中文工程写作规则

### 1. 结论先行

每个章节、每个条目的第一句给判断，背景和推导放后面。评审者按顺序读，第一句就应该知道要不要停下来细看。

```markdown
❌ 由于历史原因，配置模块在启动阶段会读取多个来源的数据，在网络不稳定的场景下，
   经过多轮讨论，我们认为有必要对现有流程做出一定的调整。
✅ 配置加载失败时改为保留上一份生效配置。此前的行为是清空配置继续启动，会让设备
   在弱网重启后丢失标定参数。
```

### 2. 每句话都要能被反驳

不可证伪的句子只消耗审查预算，不产生判断。写完一段自问：评审者能对这句话说“不对”吗？不能，就是空转句，删掉或换成事实。

```markdown
❌ 本方案在保证系统稳定性的同时，提升了配置模块的健壮性与可维护性。
✅ 配置校验失败时不再清空配置，设备保留上一份生效值并返回 `ERR_CONFIG_INVALID`。
```

### 3. 一句一事

一句话讲一件事，超过约 40 个字或出现两个以上动作就拆开。列举三项以上且有共同维度时改成表格。

```markdown
❌ 模块在收到配置后会先校验 CRC，如果校验通过则写入持久化存储并更新内存缓存，
   同时通知订阅方，若失败则回滚已写入的部分并记录日志后返回错误码。
✅ 配置写入分三步，任一步失败都回滚到上一份生效配置：
   1. 校验 CRC32；不匹配返回 `ERR_CRC`。
   2. 写持久化存储；失败返回 `ERR_STORAGE` 并丢弃本次数据。
   3. 更新内存缓存并通知订阅方；通知失败只记日志，不回滚。
```

### 4. 动词优先，去名词化

把动作写成动词，不要包成“对……进行……的处理/操作/管理”。

| 反例 | 正例 |
|---|---|
| 对下发配置进行完整性校验处理 | 校验下发配置的 CRC32 |
| 实现对非法请求的拒绝 | 拒绝非法请求 |
| 完成状态机的迁移动作 | 迁移状态机 |
| 具备处理并发请求的能力 | 可以并发处理请求 |

### 5. 删空词与套话

`为了更好地`、`有效地`、`相关的`、`一定程度上`、`整体而言`、`众所周知`、`值得注意的是`、`不断优化`、`赋能`、`闭环`（作为形容词用时）几乎总能删掉且不损失信息。删完读一遍，语义没变就是对的。

### 6. 主语显式，代词落地

`其`、`该机制`、`这一部分`、`上述内容` 只在同一句内、指向唯一时可用。跨句、跨段一律写出名字或 ID。

```markdown
❌ 该接口在其调用时需要保证它已经完成初始化，否则会影响后续流程。
✅ 调用 `config_apply()` 前必须先调用 `config_init()`；未初始化时返回 `ERR_BAD_STATE`。
```

### 7. 少被动、少翻译腔

| 反例 | 正例 |
|---|---|
| 通过引入缓存的方式来减少读取次数 | 加一层缓存，把读取次数从每次请求 1 次降到每 5 秒 1 次 |
| 基于稳定性的考虑 | 因为弱网下重试会打满连接池 |
| 在配置无效的情况下 | 配置无效时 |
| 该错误将被上层进行处理 | 上层 `session_loop()` 处理该错误 |

### 8. “的”不连用

一个名词短语最多留一个 `的`。`用于在异常场景下的配置数据的恢复的流程` → `异常场景下的配置恢复流程`。

### 9. 术语一次固定

同一概念全文一个词。首次出现给中英对照，之后固定用一种写法，并在文档开头或术语表里登记。同义词循环在小说里叫文采，在规格文档里叫歧义。

```markdown
❌ 会话建立后……链路保持期间……该连接超时后……（三个词指同一个对象）
✅ 会话（session）建立后……会话保持期间……会话超时后……
```

### 10. 中英混排与数字

- 中文与英文、数字之间加一个空格：`超时 50 ms`、`使用 CRC32 校验`。
- 标点用全角（`，。；：（）`），代码块与反引号内保持英文原样。
- 数字带单位、比较符和统计口径：`P99 ≤ 50 ms`，不写 `很快`、`基本不超过 50`。
- 已固定的技术词不翻译：`callback`、`CRC`、`DMA`、`ACK`。翻译过的词就不要再夹英文动词（不写“需要 review 一下”）。

## 文档异味速查

完整目录（识别特征、为什么阻碍审查、before/after）见 `references/doc-smell-catalog.md`。高频项：

| 异味 | 识别 | 修法 |
|---|---|---|
| 空转句 | 删掉后信息量不变 | 换成可观察事实或删除 |
| 模板复读 | 章节正文在复述模板对该章节的说明 | 写本次变更的实际内容，或写可审查的 N/A 理由 |
| 结论后置 | 关键判断埋在段落中后部 | 提到段首 |
| 术语漂移 | 同一对象出现两个以上名字 | 统一并登记术语 |
| 代词悬空 | `该机制`、`其` 跨段出现 | 写出名字或 ID |
| 名词化长句 | 一句 60 字以上，动词被包成名词 | 拆句 + 还原动词 |
| 粗体条目复读 | `- **性能：** 性能得到了提升` | 写数字与对比对象，或删掉该项 |
| 万能限定词 | `通常`、`必要时`、`原则上` 修饰硬约束 | 写触发条件；写不出就是内容缺陷 |
| 混层 | 需求条目里写函数签名、线程模型 | 移到设计层，需求只留可观察行为 |
| 无锚点断言 | “如设计所述”“见相关章节” | 补 ID 或章节路径 |
| 表格该用未用 | 三项以上并列写成长段 | 改表格，每列一个维度 |
| AI 腔收尾 | “综上所述，本方案在……的同时……” | 删掉整段；结论已经在开头了 |

## 模糊词是内容缺陷，不是措辞问题

`快速响应`、`合理的内存占用`、`必要时重试`、`尽可能保证` 这类词读起来是表达问题，实质是缺事实。改写不能修复它们：把 `快速` 换成 `及时` 只是把缺口藏得更深。

处理方式固定：保留原文，登记为 Open Question 或 finding，标注 owner，回 `devflow-specify`（阈值、验收、来源）或 `devflow-design`（契约、错误语义、时序）补齐。本技能只负责让缺口显眼，不负责让它消失。

## 工作模式

| 模式 | 入口 | 动作 | 产出 |
|---|---|---|---|
| 写初稿 | `devflow-init`、`devflow-specify`、`devflow-design`、`devflow-fix`、`devflow-ship`、`devflow-learn` 开始产出文档时自动加载 | 定判断 → 定术语 → 规范片段按模板写 → 按写作规则出文 | 第一遍就可冷读的文档，无需事后改写 |
| 作者自检 | 工件置 `ready-for-review` 之前 | 冷读测试 → 异味扫描 → 保义改写 → 登记内容缺陷 | 请求评审时附 `doc_readability_check` |
| R1/R2 评审 | `devflow-review` | reviewer 按本技能判据出 finding，只读不动手 | `reviews/` 中的 finding 与严重级 |
| 人工要求改写 | 有人反馈“看不懂” | 只改表达层，逐条给出改写点与保义证据 | 改写 diff + 未改的内容缺陷清单 |
| canonical 同步后 | `devflow-ship` 合并 delta 到 canonical | 统一术语与抽象层级，只做表达层归并 | 表达层变更单独成批，与语义合并 diff 分开 |

纪律和 `devflow-clean-code` 一致：**一个 diff 一个目的**。表达层改写和内容修订混在一次提交里，评审者无法判断哪些字是有意改的。先提交内容修订，再提交改写；或者反过来，但不要合并。

本技能不新增门禁、不新增文件、不改 `change.json`。`doc_readability_check` 是交接说明，写在评审请求里，不写进规范文档。

## doc_readability_check 返回契约

请求 R1/R2 评审时给出，reviewer 可以要求补齐。模板与验收规则见 `references/readability-check-template.md`。最低覆盖：

```markdown
doc_readability_check:
- 冷读: <五问逐条结论；哪一问不通过及原因>
- 结构: <结论先行、层级、表格化的处理结论>
- 术语: <统一了哪些漂移词；术语表位置>
- 句式: <拆了几处长句、去了哪些名词化与空转句>
- 混排: <中英空格、标点、单位与口径的处理结论>
- 保义: <未触碰的规范层清单 + ID/数值/反引号集合比对结果 + 规范关键词计数比对结果>
- 内容缺陷: <登记的模糊词、缺失事实、去向阶段与 owner；无则写 N/A 理由>
```

只写“已优化可读性”“文档已通顺”不算自检，等同没做。

初稿场景下没有被修改的既有文字，`保义` 一项写 `N/A：本次为新写内容，无既有文字被改动`，其余各项照常给结论。

## 严重级与去向

| 严重级 | 判据 | 去向 |
|---|---|---|
| `critical` | 同一条需求或契约能读出两种可执行行为；规范层被改写破坏（ID、阈值、EARS、Given/When/Then、基线摘录变形）；改写引入了没有来源的新事实 | 回作者阶段修复并复审；破坏基线摘录时回退改写 |
| `important` | 冷读测试有一问必须靠代码或作者口头解释才能回答；术语漂移导致对象不确定；关键判断被埋在段落中部；模板复读掩盖了未分析的风险 | 作者阶段返工 |
| `minor` | 局部措辞、连接词、中英空格、非 canonical 显示名的标题措辞 | 可修，也可由人接受不修，但要有 Resolution |

严重级按“评审者会不会读错”判定，不按修改工作量判定。可读性 finding 不能被降级成风格偏好来绕过门禁，也不能反过来用来卡住内容正确的文档：`minor` 不阻塞 R1/R2。

## 合理化反驳

| 话术 | 现实 |
|---|---|
| 「先写完，最后统一润色一遍」 | 事后改写要受保义约束、做集合比对、拆独立 diff，还可能改坏规范内容。写的时候换个句式几乎不花时间 |
| 「写得详细一点总没错」 | 审查预算有限。不能被反驳的句子只占版面，不产生判断 |
| 「这些话是模板要求的」 | 模板要求的是那一项判断，不是那段文字。没有内容就写可审查的 N/A 理由 |
| 「评审时他不懂可以问我」 | 独立评审拿不到作者上下文；canonical 文档半年后也没人可问 |
| 「术语用英文更准确」 | 混用才是问题。固定一种写法，首现给对照 |
| 「改写会破坏规范内容」 | 分层就行：规范层逐字不动，表达层随便改。怕破坏不是不改的理由 |
| 「先写完，可读性以后再说」 | 门禁就在下一步。读不懂的文档要么被空过，要么被整体打回，两种都更贵 |
| 「读者可以对照代码看」 | 代码不是规格。canonical 文档必须冷读可懂，否则它不再是真相来源 |
| 「AI 写的虽然啰嗦但结论是对的」 | 无法被审查的正确等于无法采信。人签不了字，门禁就没通过 |

## 自检清单

- [ ] 写之前已定判断、定术语，并确认哪些片段属于规范层、按模板写
- [ ] 冷读测试五问都能只凭文档回答；不能回答的已分类为可读性缺陷或内容缺陷
- [ ] 规范层逐字未动：ID、阈值与单位、EARS 关键词、Given/When/Then、QAS 五要素、基线摘录、selector、preservation clause
- [ ] canonical 章节标题未被顺手改写；确需改名的走 delta `RENAMED`
- [ ] 每节首句是判断；没有 AI 腔收尾段和模板复读
- [ ] 无空转句；抽查任意五句都能被评审者反驳
- [ ] 长句已拆；名词化已还原为动词；`的` 不连用
- [ ] 术语全文一致，首现有中英对照；代词都能落到唯一对象
- [ ] 三项以上的并列已表格化，每列一个维度
- [ ] 中英之间有空格，标点全角，数字带单位、比较符和统计口径
- [ ] 模糊词没有被换词掩盖，已登记为 Open Question 或 finding，并写明去向与 owner
- [ ] 表达层改写与内容修订分属不同 diff（初稿无既有文字改动时写 N/A）
- [ ] `doc_readability_check` 已给出，且每项是具体结论而不是“已优化”
