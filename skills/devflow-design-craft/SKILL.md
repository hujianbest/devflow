# DevFlow 设计匠艺（质量透镜）

## 总览

DevFlow 的设计流程节点（`devflow-component-design` / `devflow-ar-design`）负责*结构*：填齐模板章节、回指 requirement、列 Design Options、交独立评审。本透镜负责*判断*：让产出的设计不只是「章节齐全」，而是「简单、契约清晰、抽象恰当、嵌入式安全」。

资深工程师与合格工程师的差距，几乎全在这层判断里。本 skill 把这层判断编码成**可判别的 tell（坏味道信号） + 具体反例**，供设计节点在起草时随时对照。

## 它不是什么

- **不是流程节点**：不写 `progress.md`、不出现在 `next_action_or_recommended_skill`、不产生 verdict。
- **不替代独立评审**：它让你*产出更好的设计草稿*，`devflow-component-design-review` / `devflow-ar-design-review` 仍是唯一裁决者。
- **不放宽门禁**：所属节点的硬性门禁（模板章节、测试设计章节、组件边界停下规则）一律不被本透镜削弱。

## 何时叠加

| 调用方 | 在哪个步骤叠加 |
|---|---|
| `devflow-component-design` | 「方案选择 checkpoint」与「起草 / 修订设计」步骤 |
| `devflow-ar-design` | 「方案选择 checkpoint」与「起草代码层设计」步骤 |

## 核心判断

### 1. 简单性优先（Simplicity First / 抗过度设计）

起草任何设计前先问：「满足**当前 requirement** 的最简结构是什么？」起草后用 Staff 工程师视角自检：「能更少吗？这些抽象配得上它带来的复杂度吗？他会不会说『为什么不直接……』？」

| ✗ 过度设计 | ✓ 恰当 |
|---|---|
| 为一个通知场景设计带中间件管线的通用 EventBus | 一次直接的回调 / 函数调用 |
| 为两个相似状态机抽象出「通用状态机框架」 | 两个直白的状态机 + 少量共享工具 |
| 为三个配置项做「配置驱动的策略注册表」 | 三个显式分支 |
| 预留「将来可能要支持的协议」的插件层 | 只实现当前 requirement 要的那一种 |

**判别 tell**：设计里出现「框架 / 引擎 / 管线 / 注册表 / 通用 X」但当前只有 1 个真实用例 → 几乎一定过度设计。为「假想的未来需求」而非「当前 requirement」做的结构，删掉。

### 2. 抽象克制（Rule of Three）

- **第三个真实用例出现前不抽象**。两处相似代码 < 一个错位的抽象。
- 接口 / 基类 / 模板的数量应约等于**真实调用者**的数量，而不是「未来可能的调用者」。
- 抽象的成本是「读者要多理解一层」；只有当它**消除的重复 > 它增加的认知负担**时才值得。

**判别 tell**：只有一个实现类的接口 / 只有一个派生类的基类 / 只被调用一次的「可复用工具」→ 内联回去。

### 3. 接口与契约设计（Contract-First）

设计组件 SOA 接口或 AR 的关键接口时，契约必须显式，不能靠「读实现去猜」：

- **Hyrum's Law**：接口的*一切可观测行为*（返回时序、错误码、并发可重入性、副作用顺序）只要存在，下游就会依赖它。因此这些必须**写进契约**，而不是「实现碰巧如此」。
- **错误语义先行**：每个对外接口显式列出错误码集合、各错误的触发条件、调用方应如何恢复。happy path 之外的契约同等重要。
- **边界校验**：在组件 / 模块边界把外部输入当不可信处理；校验放在边界，而不是散落在内部逻辑里。
- **最小知识 / 接口隔离**：接口只暴露调用方真正需要的；不要把内部状态泄漏成公共接口。
- **兼容性策略**：`modify` / `remove` 的接口必须显式写 ABI / API 兼容判断、迁移路径或破坏式变更标记。

**判别 tell**：接口描述只写了入参和「返回结果」，没写错误码 / 并发约束 / 副作用 → 契约不完整，下游会踩坑。

### 4. SOLID / GRASP 的可判别 tell

不要只在「方法原则」里列名词。用下面的 tell 实际检查设计：

| 原则 | 违例 tell | 修法 |
|---|---|---|
| **SRP** | 一个类 / 模块有两个以上「会独立变化的理由」 | 按变化轴拆分 |
| **OCP** | 每加一种新类型都要改同一个 switch / if 链 | 用多态 / 表驱动，但仅当类型确会增长（否则别过度设计） |
| **LSP** | 子类型重写后违反父类型契约（抛新异常 / 收窄输入） | 重新审视继承关系，优先组合 |
| **ISP** | 调用方被迫依赖它用不到的接口方法 | 拆小接口 |
| **DIP** | 高层模块直接依赖具体低层实现 | 依赖抽象；但不为单实现造接口 |
| **GRASP 低耦合** | 改 A 组件必然要改 B 组件 | 检查依赖方向与边界 |
| **GRASP 高内聚** | 一个模块里的函数彼此无关 | 重新归组 |

### 5. 嵌入式防御性设计（一等约束）

DevFlow 面向 C/C++ 嵌入式，下列维度是**设计时的一等约束**，不是「编码时再说」：

- **内存与生命周期**：谁分配谁释放、所有权转移点、缓冲区边界、栈 vs 堆。
- **并发与实时性**：中断上下文限制、临界区、锁顺序与死锁规避、实时路径的有界执行时间。
- **资源**：句柄 / 文件 / DMA / 定时器的配对获取与释放；失败路径也要释放。
- **错误处理与降级**：错误如何向上传播、是否有降级路径、是否有不可恢复态。
- **ABI / 编译条件**：对外符号的兼容性、条件编译分支的可维护性。

**判别 tell**：设计文档对「失败 / 中断 / 资源耗尽 / 并发竞争」一字不提，只描述 happy path → 嵌入式设计不合格。

### 6. 有质量的方案对比（Design Options）

`devflow-ar-design` / `devflow-component-design` 要求列 2-3 个方案。本透镜要求方案对比**有质量**：

- 每个方案标注**量化或具体的取舍**（复杂度、内存 / 时延开销、可回滚性、迁移成本、长期维护），不是「方案 A 好一点」这种空话。
- 推荐方案要给**理由**，理由要落在工程事实（不是个人偏好）。
- `Single obvious option` 只在**真的**只有一条路时使用，且必须写明为什么其它方案不成立（组件设计已限定 / 接口不可变 / 变更极小）——不能用它掩盖偷懒。

**判别 tell**：三个方案只是同一方案的措辞变体 / 推荐理由是「更优雅」「更现代」→ 方案对比无效。

## 与 DevFlow 纪律的协同

- 本透镜服务于设计节点的产出质量；门禁、模板、组件边界停下规则、独立评审一律不变。
- 触及组件接口 / 依赖 / 状态机时，仍按 `devflow-ar-design` 的规则停下回 `devflow-router` 升级 `component-impact`——本透镜不会让你「因为设计得简单」就越过组件边界。
- 简单性优先**绝不**等于省略嵌入式安全维度：最简但仍正确、仍防御的方案才是目标。

## 反向理由化（Common Rationalizations）

| 话术 | 反驳 |
|---|---|
| 「先把扩展性留足，将来好加功能」 | YAGNI。为当前 requirement 设计；扩展点等第三个真实用例再加。过度抽象比重复更贵 |
| 「接口先写返回值就行，错误码以后补」 | 错误语义是契约的一半。缺错误码 / 并发约束的接口 = 不完整契约，下游必踩坑 |
| 「这个 switch 以后可能要加类型，先抽象成策略表」 | 仅当类型**确会**增长才用 OCP 结构；否则显式分支更简单 |
| 「内存 / 并发是编码细节，设计里不写」 | 嵌入式语境下它们是一等设计约束；设计不写 = 设计不合格 |
| 「三个方案太花时间，写一个 Single obvious option」 | 仅当真的唯一才允许，且必须写明其它方案为何不成立 |
| 「这层抽象更优雅」 | 优雅不是工程理由。问它消除的重复是否大于增加的认知负担 |

## Red Flags

- 设计里出现「通用 / 框架 / 引擎」但只有一个真实用例。
- 只有一个实现的接口 / 只有一个子类的基类。
- 接口描述缺错误码 / 并发约束 / 副作用顺序。
- 设计只描述 happy path，对失败 / 中断 / 资源 / 并发沉默。
- Design Options 是同一方案的措辞变体，或推荐理由是主观偏好。
- 用 `Single obvious option` 掩盖未做的方案探索。

## 自检清单（让设计草稿更好，但不替代独立评审）

- [ ] 已用「最简实现是什么」与 Staff 视角自检过复杂度
- [ ] 没有为假想未来需求引入的抽象 / 扩展点
- [ ] 每个抽象都有 ≥ 3 个真实用例或明确理由
- [ ] 每个对外接口写清了错误码、并发约束、副作用、兼容性
- [ ] 边界输入校验已设计
- [ ] 内存 / 生命周期 / 并发 / 实时性 / 资源 / 错误处理 / ABI 已作为一等约束分析
- [ ] Design Options 有量化 / 具体取舍与基于工程事实的推荐理由
