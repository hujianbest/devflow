# DevFlow Clean Design

## 一句话

> **设计的唯一敌人是复杂度。好设计不是"功能更多的结构"，而是让复杂度随需求增长得更慢的结构。**

复杂度来自两处（Ousterhout《A Philosophy of Software Design》）：

- **依赖（dependency）**：要改一处，必须先理解或同时改另一处。
- **晦涩（obscurity）**：重要信息不明显，读代码的人得猜。

它们的症状是三件让维护变慢的事：**改动放大**（一个小需求要改很多地方）、**认知负担**（理解一段逻辑要先装载一大堆上下文）、**未知的未知**（你根本不知道要改哪、不改会炸哪）。本 skill 的每一条心法，都是在压低这三个症状。

本 skill 是 DevFlow 第三层"代码内在质量"的**设计统筹**。它是被设计 authoring / 设计 review 节点**消费的判据库**，不是流程节点：不产出 `Current Stage`、`Next Action Or Recommended Skill` 等运行时字段，不产 review verdict，不替模块架构师拍板组件边界 / 接口契约，也不因"设计很干净"为由跳过任何 review 或 gate。运行时路由一律回 `devflow-router`。

## 怎么用这个 skill

设计不是"填完模板章节"就完成。每写一段结构，按下面顺序自检：

1. **先量复杂度**：这个结构让"依赖"和"晦涩"变多了还是变少了？（见 §1）
2. **做成深模块**：接口窄、实现深，把复杂度埋进去而不是漏出来？（见 §2）
3. **设计两遍**：当前这版是第一个想到的，还是从 2-3 个里选出来的？（见 §3）
4. **抽象有据**：每个接口/抽象层都有真实重复或真实变化轴撑着？（见 §4）
5. **契约可冷读**：接口的输入/输出/错误/副作用/时序/兼容性写清楚了？（见 §5）
6. **扫气味**：命中 §6 的设计气味没有？命中就按处理动作改。

深层细节（连接度量表、SOLID/GRASP 落地、更多 before/after）在 `references/design-heuristics.md`，需要时再读。

## 1. 先把复杂度量出来

不要凭"感觉优雅"判断设计。用三个可观察症状判断：

| 症状 | 你会看到 | 根因 |
|---|---|---|
| 改动放大 | 加一个字段要动 6 个文件 / 3 层 | 依赖太多、太散 |
| 认知负担 | 看懂一个函数要先读 5 个其它类 | 模块太浅、抽象漏 |
| 未知的未知 | "改这里会不会影响别处？"答不上来 | 依赖隐式、契约不清 |

**复杂度是累加的、悄悄涨的。** 没有哪一处复杂度会一次压垮系统；是几百个"就加一点点"累成了不可维护。所以设计评审要对**单次改动引入的复杂度**敏感，而不是只看"这次能不能跑"。

---

## 2. 深模块：最重要的一条

> **模块的价值 = 它隐藏的复杂度 − 它的接口带来的复杂度。**

好模块**接口窄、实现深**：用很小的接口，藏起很多复杂度。坏模块是"浅模块"——接口几乎和实现一样大，调用它和自己写差不多，纯属增加认知面。

<Bad>
```java
// 浅模块：5 个方法把内部状态全暴露出来，调用方必须按正确顺序拼装，
// "怎么用对"这件复杂度被推给了每一个调用方。
class FileReader {
  void open(String path);
  byte[] readChunk(int size);
  boolean hasMore();
  void seek(long pos);
  void close();
}
// 调用方被迫处理 open/close 配对、hasMore 循环、异常时 close……
```
</Bad>

<Good>
```java
// 深模块：一个方法吃掉了打开、循环读、关闭、异常清理的全部复杂度。
class FileReader {
  // 读取整个文件并返回内容；失败抛 IOException，内部保证句柄被关闭。
  static byte[] readAll(String path) throws IOException;
}
```
</Good>

判断深浅的快问：**调用方为了"用对"这个模块，需要知道多少它内部的事？** 知道得越少，模块越深。

常见把模块做浅的反模式：

- **直通方法（pass-through）**：A.foo() 只是转手调 B.foo()，自己不增加任何价值 → 删掉中间层，或让它真正承担一层职责。
- **配置爆炸**：靠一堆参数/选项把决策推给调用方 → 给出好的默认值，把"常见情况"做成零配置（"define errors / config out of existence"）。
- **泄漏的临时耦合**：必须按 init→use→cleanup 顺序调，否则出错 → 用 RAII / context manager / 单一入口把顺序吃进模块内部。

## 3. 设计两遍（Design it twice）

第一个想到的设计几乎从不是最好的。**对任何非平凡的模块/接口，先列 2-3 个根本不同的方案**（不是同一方案换措辞），再选。

每个方案问：哪个接口对调用方更简单？哪个把更多复杂度埋进了实现？哪个更容易在需求变化时扛住？

这正是 DevFlow 设计节点 `Design Options` 章节要承载的东西。"设计两遍"的成本是几十分钟，省下的是后面几周的改动放大。Single obvious option 只在确实没有合理替代时用，且必须写明其它方案为什么不成立。

> 选不出来时，往往是因为需求还没想清。回 §5 把契约写出来，方案的优劣常常就显形了。

## 4. 抽象要有据，不要凭空造

抽象的作用是**把"是什么"和"怎么做"分开**，让调用方只关心前者。但**错误的抽象比重复更贵**：它会把不该绑在一起的东西焊死，之后每次都要为它绕路。

引入一个新接口 / 基类 / 策略层 / 框架前，必须有下面三者之一：

1. **真实重复**：已经出现 ≥3 处真实（不是看起来像）重复（Rule of Three）。
2. **真实变化轴**：有明确、当前就存在的多实现需求（不是"以后可能"）。
3. **稳定公共契约**：这是一条对外的、需要被独立演进的边界。

判断"该不该合并/抽象"的更锋利工具是**连接度（Connascence）**：两段代码越是"一处变另一处必须跟着变"，耦合越强。抽象的目标是把强连接收进同一模块内部，只在模块之间留弱连接。度量表见 `references/design-heuristics.md`。

<Bad>
```python
# 一个真实用例，却先造了通用引擎：注册表 + 策略 + 插件加载。
class ReportEngine:
    def register(self, name, strategy): ...
    def load_plugins(self, dir): ...
    def render(self, name, ctx): ...
# 现在只有 "render_pdf" 一种报表。这层抽象没有第二个实现来证明它的形状是对的。
```
</Bad>

<Good>
```python
# 当前只需要一个函数。等出现第二、第三种报表、且它们的差异稳定了，
# 再从真实重复里"长"出抽象——那时你才知道接缝该切在哪。
def render_pdf_report(ctx) -> bytes: ...
```
</Good>

## 5. 接口契约：设计阶段必须可冷读

接口契约描述**可观察行为**，不是函数名清单。reviewer 不读实现就能判断"用对了没有"，靠的就是契约。最小契约：

| 项 | 必须回答 |
|---|---|
| 输入 / 前置条件 | 合法输入范围？调用前必须成立什么？ |
| 输出 / 后置条件 | 返回什么？调用后保证什么不变量？ |
| 错误语义 | 失败如何表达（返回码 / 异常 / 错误对象）？哪些可恢复？ |
| 副作用 | 改了什么外部状态、I/O、全局？ |
| 并发 / 时序 | 可重入？线程安全？阻塞还是非阻塞？（适用时）|
| 兼容性 / 迁移 | modify / remove 时，旧消费者怎么办？ |

**一个强力技巧：把错误"设计掉"（define errors out of existence）。** 与其让每个调用方处理一种错误，不如重新定义语义让这个错误根本不存在。例：`delete(range)` 把空区间定义为合法 no-op，而不是返回错误码——所有调用方的错误处理分支一起消失了。设计错误语义时，先问"这个错误能不能从接口里消掉"。

## 6. 设计气味 → 处理动作

命中即停，按"处理"列改；改不动就在设计里显式登记为风险/债务，交评审判。完整气味目录与重构手法见 `references/design-heuristics.md`。

| 气味 | 信号 | 处理 |
|---|---|---|
| 浅模块 | 接口和实现一样大、全是直通 | 合并层、加深、删中间人 |
| 信息泄漏 | 同一设计决策散在多个模块 | 把决策收进一个模块，对外只留接口 |
| 时序耦合 | 必须按特定顺序调用否则出错 | 用单一入口 / RAII 把顺序吃进内部 |
| 上帝模块 | 一个模块有多个独立变化理由 | 按变化理由（SRP）拆 |
| 过度抽象 | 单实现接口、单子类基类、只调一次的"通用工具" | 内联回去，等真实重复出现再抽 |
| 配置爆炸 | 一堆 flag/option 把决策推给调用方 | 给默认值，做成零配置常见路径 |
| 接口契约空泛 | 只列字段名，没有错误/副作用/时序 | 按 §5 补全可观察行为 |
| 双向 / 环形依赖 | A 依赖 B，B 又依赖 A | 引入更稳定的第三方抽象或方向倒置 |
| 抽象层错位 | 高层模块里出现底层细节（字节、寄存器、SQL 拼接）| 把细节下沉，高层只表达意图 |

## 反向理由化（Common Rationalizations）

命中任意一条 → 停下，按"反驳"动作执行。

| 话术 | 反驳 |
|---|---|
| 「先把扩展性留足」 | 扩展性来自清晰的窄接口与深模块，不来自提前造框架。多余的抽象本身就是要被维护的复杂度 |
| 「抽象一下更优雅」 | 优雅不是工程理由。必须证明它**减少**的复杂度大于**引入**的复杂度，否则就是浅模块 |
| 「接口细节实现时再定」 | 接口的可观察行为是契约，必须在设计阶段可冷读。实现时再定 = 调用方在猜 |
| 「以后可能要支持多种 X」 | "以后可能"不是变化轴。等真实的第二、第三个实现出现，抽象的形状才可信 |
| 「就一个方案，没必要解释」 | 可以写 Single obvious option，但必须说明其它方案为什么不成立——否则就是没设计两遍 |
| 「这层只是转一下手，无所谓」 | 直通层是纯认知成本、零价值，正是浅模块。删掉或让它真正承担一层职责 |

## Red Flags — 看到就回头重想

- 当前只有一个真实用例，设计里却有"框架/引擎/注册表/插件/策略体系"
- 接口方法数 ≈ 实现里要操心的状态数（浅模块）
- 调用方必须"按正确顺序"调用才不出错
- 一个设计决策需要在多个模块里同时知道
- Design Options 三个方案其实是同一方案的不同措辞
- 接口契约只有签名，没有错误语义 / 副作用 / 兼容策略
- 高层模块里出现底层实现细节

**任意一条都意味着：复杂度在涨。回 §1-§5 重新设计这一处。**

## 卡住时

| 问题 | 动作 |
|---|---|
| 不知道接缝切哪 | 先写接口契约（§5）；契约清晰后边界自然显形 |
| 觉得"必须现在抽象" | 套 Rule of Three / 连接度（§4）；不满足就先重复，登记为待观察 |
| 两个方案选不下来 | 分别写出调用方代码，谁的调用方更简单选谁（深模块视角）|
| 模块怎么拆都别扭 | 多半是按"功能/层"拆而非按"变化理由"拆；回 SRP 重切 |
| 设计涉及组件边界 / 接口契约取舍 | 这不是 clean-design 能拍板的，停下交模块架构师 / 回 `devflow-router` |

## 验证清单

- [ ] 这次改动没有引入不必要的依赖或晦涩（§1 三症状自检过）
- [ ] 新模块是深模块：接口窄、实现深、无直通层
- [ ] 非平凡接口经过"设计两遍"，Design Options 是真实不同方案
- [ ] 每个抽象有真实重复 / 真实变化轴 / 稳定公共契约支撑
- [ ] 接口契约写清输入、输出、错误语义、副作用、（适用时）并发与兼容
- [ ] 能消掉的错误已通过重新定义语义消掉
- [ ] §6 设计气味已扫过，命中项已处理或显式登记为风险
- [ ] 适用领域约束（如 `embedded-development` / `automotive-development`）已消费或明确 N/A

## 与扩展 skills、TDD 的关系

- 语言级接口 / 生命周期 / ABI / 工具链细节 → `c-coding-standards` / `cpp-coding-standards`。
- 领域级设计约束（内存、实时性、中断、资源、ASIL、SOA/MDC 等）→ `embedded-development` / `automotive-development`，它们给本 skill 增补领域设计气味。
- "设计是否更可测"属于本 skill（低耦合、可注入依赖、纯函数边界）；"测试本身是否有效"属于 `devflow-test-review`。
- 编码层的命名 / 函数 / 重构纪律 → `../devflow-clean-code/SKILL.md`。
