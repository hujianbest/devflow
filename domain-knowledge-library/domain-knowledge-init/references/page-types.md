# 页面种类

概念页存在，是因为有源证明它值得独立成页。不要预建 stub。

## 入口

`quickstart.md` 是唯一入口。它要让零背景的人和后续 agent 看懂：领域 wiki 覆盖什么、怎么组织、从哪读起。必须链到每个主要栏目和关键概念。

未写完且**证据不足或尚未成型**的领域放在文末 `## Backlog`，每条包含：领域名、源锚点、一行推迟原因。不要另开 backlog 页。已识别的领域不得只靠 Backlog 交差。

## 建议栏目

栏目跟仓库里的**系统**走：包、服务、应用、库、固件镜像。用 import、调用、共享数据和测试把相关文件收成系统，**不要把源码目录树抄进 wiki**。

先盘点有哪些系统，再只为盘点到的表面建栏目。下表是角色，不是必建清单。路径名随仓库改；没有证据的行不要建。

| 角色 | 示例路径 | 何时成立 |
|---|---|---|
| 架构 | `architecture/` | 运行时、分层、请求路径、决策记录需要独立解释 |
| 领域 | `concepts/` 或 `modules/` | 领域模块或跨页术语有自己的行为 |
| 流程 | `workflows/` | 跨系统的命名流程或用例 |
| 对外表面 | `api/`、`cli/`、`sdk/` | HTTP / RPC / GraphQL / CLI / 库导出有独立契约 |
| 界面 | `ui/` | 独立应用、控制台、管理端或页面族（没有界面就不要建） |
| 出站边界 | `integrations/` | 存储、消息、第三方、硬件、设备等出站依赖 |
| 数据 | `data/` | 权威 schema、写所有权或迁移（没有就不要建） |
| 运行与运维 | `operations/` 或 `tooling.md` | 构建、运行、发布、环境入口需要独立解释 |
| 测试 | `testing/` | 测试树、夹具或验证入口需要独立解释 |
| 原文 | `sources/` | 某份原文已被 ingest，需要编译摘要 |

多包或多服务：先按系统建目录，系统内再拆页面。一个 web 应用常见是「应用目录 + 前端/后端/数据各一页」；系统很大再按路由族、数据模型或页面族拆。纯库或 CLI 仓用对外表面 + 领域 + 架构即可，不要硬造界面或 HTTP 栏目。

栏目通常有 `overview.md` 再加若干实质页。子目录 `index.md` 只做导航，不加概念 front matter。

**大仓不得把整栏目收成仓库根上的一个文件。** 接口族、界面、命名流程在盘点达到 [coverage-gates.md](coverage-gates.md) 阈值时必须是目录；各单位一页。总览里的表格不算覆盖。

单文件空壳目录（里面只有一句备注）应合并。小范围（大约不超过 10 个主源）仍可 `quickstart.md` 加至多 1–2 个支持页。

## 一页一义

每个概念一个规范页。别处只链过去，不复制解释。
正文里的 Markdown 链接才是关系边；目录位置、标签、index 链接不算语义关系。
关系写在解释它的那句话里，例如「分发给」「依赖于」「由……配置」。不要为了把图变密而互链。

每页要有解释价值：做什么、为什么存在、从哪读起、改时注意什么、关键源路径。流程/生命周期/数据模型用 Mermaid，图形必须有源。图过期等于主张过期，改句子时同步改图。优先 `flowchart` / `sequence` / `state` / `er`。节点 id 不要用 `end`；标签里的 `<>` 要加引号或改成文字。

## 禁止

- 为了「结构完整」建空页；
- 把 `.discovery/` 笔记或子 agent 原文贴进概念页；
- 持久化 commit hash 列表，除非某次提交本身解释了重要历史决策；
- 把 `INSTRUCTIONS.md` 当成文档栏目，或创建 `reviews/`；
- 用 8 页上限、Backlog 或总览表格代替已识别领域的页面。
