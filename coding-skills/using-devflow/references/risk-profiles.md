# DevFlow 风险 profiles

## 选择规则

在创建 `change.json` 时评估本次增量，而不是给组件永久贴标签。选择命中最高风险触发器的 profile，并在 `profile.reasons` 写可验证事实。

无法判断某触发器是否成立，且它会改变 reviewer、证据或专家确认要求时，先询问。不要用“改动行数少”覆盖接口、数据、安全或不可逆风险。

所有 profile 都保留完整工件、R1/R2/R3、canonical sync 独立复核、人工确认、DoD 和归档门禁。profile 只改变内容深度和附加证据。

## `standard`

适用于风险为 `low` 且同时满足：

- 影响限于组件内部，不改变公开接口、协议、错误语义或持久化格式；
- 不涉及权限、安全边界、敏感数据或监管要求；
- 不改变并发模型、实时预算、资源上限或部署拓扑；
- 回滚路径明确，失败影响局部；
- 现有自动化测试能覆盖主要回归面。

最低附加要求：

- 一个独立 generalist reviewer；
- 单元测试和受影响集成测试；
- 可核的回滚说明；
- traceability 全闭环。

## `elevated`

任一以下事实成立时使用，风险为 `medium`：

- 修改公开 API、IDL、协议、错误语义、配置兼容性或 schema；
- 修改状态机、持久化、数据迁移、并发、缓存一致性或重试行为；
- 改变构建、打包、部署、启动、升级或回滚路径；
- 影响多个组件或存在已知并行变更；
- 引入新的外部依赖、资源预算或性能阈值；
- 失败可能造成明显服务降级或较大回归面。

在 `standard` 基础上增加：

- 接口/数据/运维中适用领域的独立 reviewer；
- 兼容性、失败路径和回滚测试；
- 集成或端到端证据；
- base revision 后并行变化的显式检查；
- 对资源、性能或迁移声明提供可重复证据。

## `critical`

任一以下事实成立时使用，风险为 `high`：

- 影响安全边界、认证授权、密钥、隐私或高敏感数据；
- 影响功能安全、实时控制、硬件保护或法规合规；
- 包含不可逆数据变换、不可自动回滚发布或大范围状态迁移；
- 失败可能导致人身、资产、重大生产或供应链影响；
- 需要突破现有架构边界或接受已知重大风险。

在 `elevated` 基础上增加：

- 至少两个相互独立的 reviewer，其中一个具备命中领域的责任或资质；
- 威胁模型、安全/安全性分析或等价的领域风险分析；
- 故障注入、恢复演练、迁移彩排或适用的实机证据；
- 负责人对残余风险、回滚限制和发布窗口的明确确认；
- 任何缺失阈值、错误语义、所有权或失效策略均为 blocking。

## Profile 变更

实现或评审期间发现更高风险触发器时：

1. 更新 `change.json.profile.name`、`risk`、`reasons`、证据和 reviewer 要求；
2. 将受影响 gate 重新打开为 `pending`；
3. 补齐新增证据和独立评审；
4. 在 review record 与 `closeout.md` 说明升级原因。

不得为绕过门禁而降级 profile。风险确实降低时，记录改变风险事实的设计或范围决策，并由人确认后再降级。
