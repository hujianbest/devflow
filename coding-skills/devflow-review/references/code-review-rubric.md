# R3：代码评审 Rubric

> 评审对象：本 change 的实现 diff。上游：`srs.md`、两份 delta、canonical 基线、`tasks.md`、`traceability.md`、适用编码与领域规则。
>
> 核心怀疑：**代码是否只实现批准的增量，并在错误路径、资源路径和既有语义上保持诚实？**

## 正确性与一致性（不过 = critical）

- [ ] 实现逐项覆盖 delta-design；设计 N/A 时实现确实只是恢复 canonical 已定义行为
- [ ] 没有 SRS/delta 之外的可观察行为、接口、默认值或兼容变化
- [ ] 修改/删除语义按批准内容落地，未破坏应保留的 canonical 行为
- [ ] 边界条件无 off-by-one、截断、溢出、状态遗漏或依赖不可达分支
- [ ] `traceability.md` 的 Task、Code/Test、Evidence 与实际 diff 一致
- [ ] 实现偏离工件时先回上游修订并重新评审，不以“代码能工作”放行漂移

## 错误路径与资源（优先细读，不过 = critical）

- [ ] 每个可失败调用被检查，忽略错误有明确契约理由
- [ ] 每条失败路径释放已获取资源，且失败后状态满足设计保证
- [ ] 错误在正确边界翻译、传播或处理，无吞错和丢失上下文
- [ ] 获取/释放、注册/注销、锁/解锁、分配/回收成对

## 并发与生命周期（适用时）

- [ ] 共享状态受正确保护，锁顺序一致，临界区没有不必要阻塞
- [ ] 中断、线程、异步回调和取消时序符合 delta/canonical design
- [ ] 跨边界数据的所有权与存活期正确，无悬垂、重复释放或泄漏

## Clean Code 与设计纪律

- [ ] 命名表达完整行为，布尔为肯定语义，量带单位
- [ ] 函数职责单一、抽象层一致；控制流优先主路径，无隐藏复杂度
- [ ] 无裸魔法值、死代码、注释掉代码、test-only 后门或吞错
- [ ] 无未批准的新抽象、单实现接口、配置点或依赖
- [ ] 重复只在表达同一知识时提取，不为外观相似强行抽象
- [ ] 热路径无有证据的 N+1、无界读取、重复计算或资源风险
- [ ] 测试代码同样可读、稳定且不过度抽象

以下不是风格小问题：误导命名导致调用方误解、吞错、失败状态违约、隐藏多职责的大函数、未批准抽象、test-only 生产后门、已证实的无界资源风险。按 critical/important 处理。

## 范围与 diff 卫生

- [ ] diff 只触及 `tasks.md` 声明范围；无顺手重构、格式化或邻近修复
- [ ] 变更文件都能回指任务和需求；路过问题有独立去向
- [ ] 完整构建无新增警告，静态分析新增项已修复或有精确抑制理由
- [ ] 适用 `<language>-coding-standards`、领域技能和 `devflow-clean-code` 已实际检查

## Verdict 指引

- 行为、错误路径、资源、生命周期或工件一致性失败 → `需修改`
- 问题源自 delta-design 或 canonical design 错误 → `重新设计`，指向 `devflow-design`
- 问题源自 SRS/delta-spec → `重新设计`，指向 `devflow-specify`
- 普通测试/实现/整洁问题默认返工 `devflow-tdd`
