# 集成缺口与待决问题

## 当前组件边界

输入材料只包含：

- 一个订单数据类；
- 一个订单状态枚举；
- 一个同步取消方法；
- 两个单元测试场景；
- 一个最小 OpenAPI 操作声明。

未发现 Web 框架入口、数据库、仓储、消息系统、支付或库存集成。

## 风险登记

| 风险 | 当前证据 | 影响 | 建议确认 |
|---|---|---|---|
| 只修改内存对象 | `cancel` 直接赋值，无仓储 | 请求结束后可能不保存 | 明确持久化边界 |
| 支付后取消无退款逻辑 | `PAID` 可直接转 `CANCELLED` | 订单与资金状态可能不一致 | 明确退款编排与失败策略 |
| 无并发控制 | 无版本/锁/事务材料 | 发货与取消可能竞态 | 明确原子状态转换 |
| 通用异常 | 使用 `ValueError` | 错误映射和可观测性不稳定 | 定义领域错误 |
| 契约响应过少 | 只有 200/409 描述 | 客户端难以稳定处理错误 | 补齐响应 schema |
| 测试覆盖不完整 | 仅 PAID 成功、SHIPPED 失败 | CREATED/CANCELLED 行为可能回归 | 增加边界测试 |

## 待决问题清单

### 业务

- 哪些角色可以取消订单？
- 取消窗口是否受时间、商品类型、履约方式或商家政策影响？
- 已支付订单是否必须退款成功后才能进入 `CANCELLED`？
- 已发货订单的后续流程是什么？
- 重复取消是否幂等？

### 技术与契约

- 订单从哪里读取并保存？
- 409 是否只代表状态冲突，错误体中的稳定机器码是什么？
- 不存在订单返回 404 还是其他响应？
- 如何处理取消与支付/发货的并发？
- 是否发布 `OrderCancelled` 事件，如何保证与状态提交一致？

所有问题均保持“待确认”，没有根据常见电商实践替团队作出决定。
