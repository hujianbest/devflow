# 取消订单能力

## 能力概览

当前唯一实现能力是基于一个已加载的 `Order` 对象执行同步取消。实现位于 `OrderService.cancel(order)`。

## 当前实现事实

### 前置条件

- 调用方必须传入一个 `Order` 参数；代码没有显式的 `None` 或类型检查。
- `order.status` 必须是 `CREATED` 或 `PAID`。

### 成功结果

- 传入对象的 `status` 被原地设置为 `CANCELLED`。
- 方法返回该对象。
- `PAID` 成功取消由测试显式覆盖。

### 失败结果

- 对 `SHIPPED` 和 `CANCELLED`，集合判断会进入拒绝分支并抛出 `ValueError`。
- `SHIPPED` 拒绝由测试显式覆盖。
- 异常消息固定为 `order cannot be cancelled in current status`。
- 方法自身没有把异常转换成 HTTP 409。

证据：`src/order_service.py:18-23`; `tests/test_order_service.py:6-14`。

## 场景表

| 场景 | 输入 | 当前代码结果 | 证据强度 |
|---|---|---|---|
| 已创建订单取消 | `Order(status=CREATED)` | 状态改为 `CANCELLED` | 代码分支，未测试 |
| 已支付订单取消 | `Order(status=PAID)` | 状态改为 `CANCELLED` | 代码与测试 |
| 已发货订单取消 | `Order(status=SHIPPED)` | 抛出 `ValueError` | 代码与测试 |
| 已取消订单再次取消 | `Order(status=CANCELLED)` | 抛出 `ValueError` | 代码分支，未测试 |

## 对外契约意图

OpenAPI 声明 `POST /orders/{orderId}/cancel`，成功为 200，当前状态不可取消为 409。该契约与领域方法的总体意图相符，但输入中没有 HTTP 控制器、订单加载、异常映射或响应序列化代码，不能声称端到端接口已经实现。

## 候选业务语义（未确认）

- 取消是一个命令，而不是对订单资源的常规更新。
- 已取消订单再次请求可能适合幂等成功，而不是冲突；当前实现选择抛异常，但材料没有解释业务政策。
- 已支付订单取消可能需要退款、账务冲正和通知。
- 已创建订单取消可能需要释放库存或优惠额度。
- 不允许已发货订单取消可能是因为它应转入退货/售后流程。

## 业务验收前必须回答

1. 谁可以取消，是否区分客户、客服、商家和系统？
2. 取消是否需要原因、备注、操作者和时间戳？
3. 已支付取消如何退款，失败时订单状态如何处理？
4. 重复取消应返回成功、409，还是返回原取消结果？
5. 与支付或发货并发时，哪一个操作获胜，如何防止竞态？
6. 是否需要审计事件、领域事件或外部通知？
