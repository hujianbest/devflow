# Agent 知识库怎么建

今年把 Karpathy 的 LLM Wiki 笔记、Anthropic 的上下文工程、Letta 的 Context Repositories、Cline Memory Bank 和 Google 的 OKF 对过一遍，发现一件有点扫兴的事。大家吵向量库、图谱、自动维护 Wiki，真正收敛下来的做法很土，而且几乎都在 git 里的 Markdown 上。

如果你也想给 Agent 建知识库，尤其是给一个存量系统用，下面是我现在会按这个顺序做的事。

## 先别从检索开始

多数团队一上来就问检索怎么做。向量还是关键词，要不要 GraphRAG。这个问题问早了。

Karpathy 在 2026 年 4 月那份 gist 里把对照写得很清楚。RAG 每次从原文碎片重拼答案，拼完就散，下次再拼一次。Wiki 是另一条路。新材料进来时，先合并进已经存在的概念页，交叉引用和矛盾当场处理。以后问的是编译过的页。

他举过一个量级。一份材料可能要改十到十五个 wiki 页。`index.md` 是目录，每条带链接和一行摘要。`log.md` 按时间追加。查询时先读目录，再钻进正文。他写到大约一百份材料、几百页时，这套东西够用，不必先上 embedding。

所以建设的第一件事，是决定知识在什么时候合成。写的时候合成，问的时候复用。问的时候再发现，库永远长不起来。

## 文件系统已经是检索

Letta 在 2026 年把记忆改成了 git 上的文件系统，他们叫 Context Repositories，文档里也叫 MemFS。目录树常驻提示词，`system/` 以外的文件要读才进上下文。默认没有向量索引。Agent 用普通的读文件和搜索找东西。

这就是检索本身。Coding Agent 本来就会 `grep`、会按目录走、会看文件名。目录是索引，文件名是路由，frontmatter 是过滤条件，git 是时间轴。

再包一层专有 catalog SDK，等于把已经会用的原语锁死。规模真把目录扫不过来，再加 BM25 或向量。跨概念的多跳问题被黄金问题证伪以后，再谈局部图。2026 年几份综述把这条阶梯写得很齐，跳级上 GraphRAG 是最常见的过度建设。

Wiki 和现场检索也不打架。领域语言、规则例外、设计动机、跨系统流程，这些要综合，现场从代码切片拼不出来，适合编译进知识页。当前函数怎么写、某个调用点在哪、生产配置现在是什么值，现场去仓库或配置中心看，比镜像进知识库更不容易漂。OKF 的 `resource` 字段就是为了指向真源。

## 每次只给最小的那一组

Anthropic 在 2025 年 9 月那篇《Effective context engineering for AI agents》里把这件事说死了。上下文会腐烂。token 越多，模型从这段上下文里准确回想的能力越差，他们叫 context rot。注意力是有预算的，每多一个 token 都在花这笔预算。好的做法是每次只塞进最小的、信号最强的那一组。

他们推荐的读法也很具体。先留轻量标识，路径、查询、链接，需要时再用工具把正文捞进来。Claude Code 就是这种混合。`CLAUDE.md` 会预先放进上下文，仓库本身靠 glob 和 grep 即时去读。

Cline 的 Memory Bank 早期要求每个任务先读完全部记忆文件。官方最佳实践里现在还能看到那句 MUST read ALL memory bank files at the start of EVERY task。社区后来把它当成反例。那是把工作记忆一次性倒进注意力预算。目录可以常驻，正文按需。

Agent Skills 也是同一条纪律。`description` 大约一百个 token 常驻，用来决定要不要加载。技能正文只在任务对上时才读。教 Agent 怎么维护知识的流程，和知识正文本身，不要塞进同一个永远加载的文件。

## 三种东西寿命不同，分开放

规则改得慢，领域事实却会过期。流程更是偶尔才走一遍。这几样塞进同一个文件，上下文很快又胖又脏。存放用文档还是向量，反倒是后一步的事。

始终加载的，是跨任务都成立的规则。知识从哪进、draft 怎么标、什么时候拒答、权威谁说了算。AGENTS.md 或 CLAUDE.md 官方建议压在五十到两百行。能推迟的一律推迟。

按需加载的，是偶尔才走的程序。冷启动、摄入、审核晋级，各自写成 Skill。Skill 回答怎么做，不回答业务上是什么。

查询时钻取的，才是会过期的领域事实。一概念一文件，先看目录和摘要，再看概念页，最后回原文。知识回答是什么、为什么。

混在一起会出现三件事同时发生。上下文变胖，流程污染事实，事实被当成指令。Cline 那种每次全读，就是把短寿命的进度笔记和长寿命的领域规则捆在一起了。

任务里的工作笔记，当前目标、试过什么、下一步，留在会话或任务目录。只有经过回写、通过校验，才进知识库。会话本身不能当来源。

## 人决定真假，机器记账

Karpathy 偏向让 LLM 把 wiki 整层写完。评论区反对得很集中。编译层一旦写进幻觉，错误会复利。查询不再回原文，比每次 RAG 更危险。

LLM 擅长改十五处交叉引用。它不擅长当无监督的真相源。机械事实可以机器验证后发布，路径、签名、Topic、表结构。业务语义，术语、边界、规则例外、兼容原因，必须有人点头才能变成 stable。

冲突不要自动选边。代码说明现状，文档说明意图，两边都挂上，等负责人判断是漂移、兼容路径，还是迁移没做完。Agent 的工作是记账，把来源、时间和差异写清楚。

draft 可以立刻被检索到。审核只管晋级，不管能不能读。回答里用到 draft，必须标明未确认，并给出那一页的路径。安全、资金、权限、发布这类高风险的 draft，只能当候选，不能写成可执行策略，也不能直接落成代码。

## 冷启动只出骨架

从代码自动还原完整领域模型，社区几乎没人把它当默认路径。主流仍是文档摄入，再加上现场去读代码。如果你的系统是存量的、文档和代码会打架，从仓库抽骨架仍然值得做，但不要假装 Agent 能自动确认 Bounded Context。

冷启动我现在只要求四件事。

仓库钉死到某个 commit，扫描范围和敏感路径先写死。只做静态只读扫描，不跑仓库里的脚本和构建。

盘点留下事实。语言、构建根、契约文件、迁移、测试、CI、CODEOWNERS、入口线索。失败和未知也记下来，不要补成故事。

系统侧只出 Repository、Application、Module。页面上写入口清单，指向 OpenAPI、Topic、主表、开关名，不把每个接口做成一页。业务侧提出候选的上下文、术语、流程、规则，全部标成 draft，推断必须写明这是推断。

对账时把仓库里已有文档的主张拆开。支持代码的、补充意图的、互相打架的、目标态的、历史的、看不懂的。打架的单独挂出来。

退出看四条能力够不够。Coding Agent 能从目录走到正确的应用和模块，再回到仓库。Design Agent 不带代码仓也能说出某个上下文的边界、术语、主要流程和已知规则，并标明哪些还没确认。每条机械事实带着 commit 或契约版本。冲突和未知可见。

接口、表、配置的细页，留给以后按风险深化。事故半径大、涉及资金权限、变更频繁、被多个上下文调用的，先做。用户说把所有接口都建成页面，停下来，问他具体范围。

## 每个任务都要会读，也要会写回

建设完以后，知识库会不会变老，取决于任务结束时有没有回流。

读的顺序固定。先看根目录，每条带类型、一行摘要、状态、视图、负责人。确定候选上下文之后，再读领域或系统的概述。判断相关，才读少量概念正文。高风险、互相打架、或概念页不够用，才回代码、契约、ADR、制度原文。

没有代码仓的设计任务，走到需要字段类型、状态枚举、具体接口形状时停。说明缺仓库，或者把问题转给实现侧。有代码仓的实现任务，用骨架页上的精确名字回仓库搜，读契约原文，不要在知识库里找第二份接口文档。

任务中出现下面这些情况，必须写成提案，不要直接改知识正文。两页概念互相矛盾，或概念和真源矛盾。目录把人带到了错的上下文。任务依赖一条库里没有、但决定了做法的规则。做了会影响后续任务的取舍。某条已经确认的知识被刚合并的代码推翻。

提案里只留结论、证据锚点和来源。试错过程、会话摘要、密钥和个人信息不要放。提案由维护流程合并，晋级仍然由人决定。

没有这些发现，就明确写一句无需回写。空提案比不写更糟。

## 明天就能开工的最小集合

一个可发布的知识目录，一概念一文件，带 `index.md` 和 `log.md`。

一份极瘦的入口说明，告诉 Agent 知识在哪、draft 怎么标、什么时候拒答、发现了矛盾写到哪。

一份维护流程，覆盖冷启动、摄入、跟代码同步、审核、体检。摄入时按新、支持、补充、替换、冲突、替代、无关分类，禁止一份材料生成一篇摘要。

一份任务时的读写约定。怎么按目录往下钻，什么必须写回。

一个校验脚本，检查必填字段、来源是否钉了版本、stable 有没有对应的确认、实现细节页是不是只有被明确要求深化时才出现。

Cursor 这类宿主还可以加 hooks。会话开始注入入口。读到 draft 或过期页时提醒。没有维护锁时拦住对知识正文的直接写入。任务结束如果读过知识却没写提案，追问一次。没有 hooks 的环境，把同样的规则写进入口说明，效果会差一截，但方向一样。

向量库、图谱、全量类和方法文档、生产配置镜像、让 Agent 自己把推断标成已确认，这些都可以后做，有些不该做。

知识库首先帮 Agent 少猜错落点，少碰不该碰的规则，看得出一条结论从哪来，还记得昨天已经发现过的矛盾。它替代不了代码、测试、契约和配置中心。建到能完成这四件事，就可以让两个 Agent 开始用。用的过程会比规划时更能告诉你，下一步该深化哪一块。
