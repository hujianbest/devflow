# 设计·开发·测试全流程 AI 辅助研发变革方案

> 面向：仍按设计 / 开发 / 测试三段分工、并以 IR→SR→AR 开展交付的车规 / IPD 团队。
>
> 本文回答四件事：全流程人机怎么分工、文档怎么跟传统流程兼容、知识怎么形成飞轮、交付小团体怎么组。
>
> 工程落地侧可与本仓库 DevFlow（SDD → TDD → Clean Code，human-on-the-loop）对齐；上游系统工程与下游系统测试需要在同一套追溯链上扩展，而不是另起一套工具叙事。

---

## 0. 先说判断

你们现在的模式是典型的**职能烟囱 + 文档接力**：SE 写需求分析 / 功能设计，开发写实现设计再编码，测试按 SR 写规格与用例再验收。每段都有自己的「串讲」，信息损耗发生在交接口，而不是写代码那一刻。

业界 2025–2026 的主流不是「给每人发一个编程助手」，而是三件事叠在一起：

1. **Spec-Driven Development（规范驱动）**：规格成为人与 AI 的共同真相源；代码是规格的下游产物，而不是聊天记录的偶然结果。Microsoft Spec Kit、Thoughtworks 的 SDD 实践，核心都是先对齐意图，再加速执行。
2. **Human-on-the-loop**：具体生产交给 AI，人站在环上审查规格、设计、测试证据与架构边界。这和「人机并肩敲每一行」不同；人的时间花在判断上。
3. **知识工程（图谱 + 归档工件 + 反馈闭环）**：纯向量检索不够。要把 IR/SR/AR、接口、代码、测试、缺陷、决策串成可查询关系；每次交付再回写，下一轮 Agent 才用得上历史。

对你们团队，变革的靶心不是「消灭文档」，而是：

> **把文档从「给人读的叙事」改成「给人审、给 AI 执行的契约」；把三段串讲改成同一条可追溯交付链上的门禁。**

车规 / IPD 约束（功能安全上抛、版本基线、追溯矩阵、SIL/HIL）不能被 AI 流程绕开。正确做法是：**合规需要的证据继续产出，但生产过程尽量由 AI 起草、人签字确认。**

## 1. 现状诊断：瓶颈在哪里

| 环节 | 传统做法 | 实际成本主要花在哪 | AI 能立刻帮什么 | AI 不能替什么 |
|---|---|---|---|---|
| IR→需求分析 | SE 手写，IR 拆 SR | 边界澄清、冲突消解、跨域权衡 | 草稿、差距分析、追溯初稿 | 产品取舍、安全目标确认 |
| SR→功能设计 | SE 拆 AR，写功能设计说明书 | 接口契约、场景完备性 | 候选 AR 切分、接口草案、影响面 | 架构拍板、ASIL 决策 |
| AR 串讲→实现设计 | 开发听讲后写时序/类图/UT | 理解偏差、设计与代码双写 | 从 AR+设计生成实现设计与 UT 骨架 | 组件边界、跨 ECU 协调 |
| 编码与 CR | 人手写 + 审查 | 样板代码、局部一致性 | 按设计 TDD 实现、自检、diff 说明 | 最终合入责任 |
| SR 测试串讲→规格 | 测试听讲后写测试规格 | 场景遗漏、与需求漂移 | 从 SR/AC 生成测试规格与用例 | 风险优先级、放行决策 |
| 自动化与回归 | 人手写脚本、问题单闭环 | 用例维护、回归成本 | 用例生成、失败分类、修复草案 | 实车/HIL 环境判定 |

三个结构性问题：

1. **同一意图被翻译了三次**：需求分析 → 功能设计 → 实现设计 → 测试规格。每次翻译都可能改义。
2. **串讲是瞬时知识**：讲完就散，下一轮 AR / 新人 / 新 Agent 接不住。
3. **验收粒度与实现粒度错位**：开发按 AR 合入，测试按 SR 验收，中间缺「可执行验收契约」把两边钉死。

目标态要解决的是这三件事，而不是多几个 Copilot 席位。

## 2. 目标态总览

### 2.1 一条交付链，而不是三段流水线

```text
IR（业务/整车意图）
  └─► SR（系统可验收行为）          ← 系统工程主战场
        ├─► AR₁ / AR₂ / …（可独立合入的工程变更）  ← 工程交付主战场（DevFlow）
        │     └─► 代码 + UT/组件测 + 追溯证据
        └─► SR 验收包（测试规格/用例/自动化/HIL） ← 验证主战场
              └─► 与所有相关 AR 的 AC / 证据对齐后放行
```

原则：

- **SR 是系统验收的合同单位**（对测试、对客户、对基线）。
- **AR 是工程变更与合入的合同单位**（对开发、对代码仓、对 CR）。
- **每条验收标准（AC）必须能落到具体 AR 与可执行测试**；SR 验收 = 其下全部 AC 证据齐全，而不是再开一场「感觉讲清楚了」的串讲。

### 2.2 人机协作总原则

| 原则 | 含义 |
|---|---|
| AI 生产，人确认 | 草稿、分解、代码、用例、报告默认由 AI 产出；门禁结论由人签 |
| 规格先于代码 | 没有可测试规格与范围边界，不进入实现 |
| 作者不自审 | 规格/设计/代码/测试评审用独立上下文（人或独立 Agent），作者不给自己放行 |
| 上抛不可省略 | ASIL、跨 ECU 契约、整车电源/网络策略等仍走功能安全 / 架构 owner |
| 证据进仓 | 聊天不算完成；工件、门禁状态、追溯进仓库或配置库 |

任务分成三类：

- **AI 主责（人抽检）**：格式化起草、样板实现、用例展开、回归执行、文档同步、缺陷初分类。
- **人机共责（人必须过门禁）**：需求边界、AR 切分、接口语义、架构与安全相关设计、测试策略与放行、CR 合入。
- **人主责（AI 仅辅助检索）**：产品优先级、安全目标确认、重大架构变更、量产放行、对外承诺。

## 3. 问题一：全流程人机分工与流程建设

下面按你们现有四段作业展开。每段给出：输入、输出、谁干、门禁、和上下游怎么接。

### 3.1 设计段：IR → SR → AR

#### A. IR 澄清与需求分析说明书

| 项 | 内容 |
|---|---|
| 输入 | 原始需求、竞品/法规/整车场景、既有系统基线 |
| AI 做 | 抽取意图与约束；列出歧义与冲突；生成 IR 条目化草稿；对照历史同类需求做差距分析；生成「待确认问题清单」 |
| 人做 | SE / 产品拍板范围、优先级、非目标；确认法规与安全相关表述 |
| 共责门禁 | **G0 IR 准入**：范围清晰、关键 Open Question 关闭或显式挂起并有 owner |
| 输出 | 结构化 IR 包（见第 4 节），而不是长篇散文 |

串讲可以缩成 **IR 评审会**：会前 AI 已出差距清单，会上只决未决问题。

#### B. IR → SR 分解与系统需求

| 项 | 内容 |
|---|---|
| AI 做 | 按场景 / 接口 / 状态机候选拆 SR；为每条 SR 写可观察行为与初版 AC（Given/When/Then）；建立 IR↔SR 追溯草稿；标出跨 ECU / 诊断 / 电源相关项 |
| 人做 | SE 确认 SR 边界与依赖；功能安全 / 架构确认需上抛项；拒绝「实现细节混进 SR」 |
| 共责门禁 | **G1 SR 冻结（可增量解冻）**：SR 可测试、可追溯、无 blocking 歧义 |
| 输出 | SR 规格（行为 + AC + NFR + 来源） |

判断标准：一个不熟悉业务的测试工程师（或测试 Agent）只读 SR，应能写出验收意图，而不需要再听一遍「口头补充」。

#### C. SR → 功能设计与 AR 分配

| 项 | 内容 |
|---|---|
| AI 做 | 基于组件 canonical 设计（若已有）做影响分析；提案 AR 切分（按可独立合入、可独立验证）；输出功能设计增量：职责、接口、错误模型、状态、与既有 SR 的映射 |
| 人做 | 模块架构师 / SE 确认 AR 切分与接口；协调跨团队消费者；拒绝过大或碎片化的 AR |
| 共责门禁 | **G2 AR 就绪**：每个 AR 有范围、非范围、上游 SR/AC 锚点、风险 profile |
| 输出 | 功能设计说明书（可机读增量）+ AR 清单 |

**AR 切分经验法则（供人和 AI 共用）：**

- 一个 AR 最好对应一个组件（或明确的少量组件）上的一条可合入变更。
- AR 必须能写出可测试 AC；「纯调研」「纯文档」不要占 AR 号，另立工作项。
- 跨 ECU 信号 / 服务契约变更单独成 AR 或显式子项，并列出消费者 owner。

传统「SE 组织开发串讲」改为：

1. AI 生成 **AR 交接包**（SR 摘录、AC、接口 diff、风险、Open Question）。
2. 短会只确认分歧；录音/纪要回写到 AR 工件，禁止「只存在于听众脑子里」。

### 3.2 开发段：AR 实现设计 → 代码 → 合入

建议工程段直接采用规范驱动交付（与 DevFlow 对齐）：

```text
baseline → specify(srs+delta-spec) → R1 → design(delta-design+测试设计)
  → R2 → TDD(RED/GREEN/REFACTOR) → R3 → ship(canonical sync + 归档)
```

| 阶段 | AI 主责 | 人机共责 | 人主责 |
|---|---|---|---|
| 基线 init | 从代码逆向 draft spec/design | 澄清 unknown | 确认 baseline-ready |
| 实现规格 | 写 srs / delta-spec / 追溯 | R1 评审 | 业务/接口事实确认 |
| 实现设计 | 时序/结构/错误模型/UT 设计 | R2 评审 | 架构边界、安全机制 |
| 编码 | 按任务 TDD 实现与自检 | R3 测+码评审 | 合入签字、发布相关决策 |
| 缺陷 | 复现、根因草案、最小修复 | 确认根因与范围 | 是否进版本、是否升级严重级 |

相对传统流程的变化：

- **实现设计说明书**不再先于代码「写死一大本」，而是变成 `delta-design.md`：相对当前组件设计的增量 + 测试设计。归档时同步回组件长期设计真相。
- **UT 用例**在设计门禁就要定 Given/When/Then；实现必须先红后绿，避免「补测试自欺」。
- **代码审查**保留，但前置已有 R1/R2；CR 聚焦行为证据、风险与可读性，而不是从零理解需求。

开发串讲可以取消为常态；改为 **AR Kickoff 15 分钟**（可选）+ 异步评审。新人靠工件冷读上手，而不是靠「谁给我讲过」。

### 3.3 测试段：按 SR 验收，但吃 AR 的契约

测试仍以 **SR** 为验收单位，这与车域 / IPD 一致。变的是输入质量与生产分工。

| 步骤 | AI 做 | 人做 | 门禁 |
|---|---|---|---|
| SR 输入对齐 | 从已冻结 SR + 相关 AR 的 AC/追溯生成「验收范围图」 | 测试负责人确认风险与环境层级（UT/SIL/HIL/实车） | **T0 策略评审** |
| 测试规格 | 生成测试规格草稿（场景、等价类、边界、负向、状态） | 测开 / SE 修订优先级与豁免 | **T1 规格评审** |
| 用例与自动化 | 生成用例表与自动化骨架；映射到 AC ID | 维护框架、环境、不稳定用例治理 | **T2 用例基线** |
| 执行 | 触发流水线、聚类失败、草拟问题单 | 判定环境问题 vs 产品缺陷；严重级 | — |
| 回归与放行 | 回归计划、证据包汇总 | **SR 放行签字** | **T3 SR 验收** |

SE「向测试串讲 SR」改为：

- 测试 Agent / 测开直接消费 **已 R1 通过的 SR/AC** 与 **已合入 AR 的证据**。
- 仍保留一次 **SR 验收启动会**，但议程是风险与环境，不是重新讲需求故事。

问题单回流：

```text
失败证据 → AI 分类（产品/用例/环境/已知）→ 人确认
  → 产品缺陷进入 AR fix 旁路（复现测试先行）
  → 用例问题回写测试规格（知识沉淀）
  → 关闭时更新 SR 验收证据包
```

### 3.4 端到端流程怎么建（可执行视图）

```text
[产品/SE] IR 包 ──G0──► SR 规格 ──G1──► 功能设计+AR 清单 ──G2──►
    对每个 AR：
        [工程小队] DevFlow 闭环 ──合入──► 组件基线更新
    [测试小队] 聚合相关 AR 证据 ──T0..T3──► SR 验收完成
    全程：追溯矩阵 IR→SR→AR→Spec→Test→Evidence 自动维护
```

**流程建设清单（落地时要写进团队规章）：**

1. 统一 ID：`IR-xxx` / `SR-xxx` / `AR-xxx` / `AC-xxx` / `TC-xxx`，禁止口头别名充当主键。
2. 统一仓结构：组件级 `specs/` 真相 + 变更目录；系统级 SR 库与追溯索引可分库，但 ID 必须打通。
3. 统一门禁状态机：`pending / blocked / rework / passed`，状态进工件，不进聊天。
4. 统一 Agent 角色：主控编排、实现、评审分离；作者不自审。
5. 统一运行模式：日常 `attended`（人确认关键门禁）；成熟后部分低风险 AR 可 `unattended` 连跑，但 critical 与归档确认仍需人。
6. 工具链最小集：需求/缺陷系统 ↔ Git 工件双向链接；CI 跑测试并回写证据；可选 MCP 暴露知识检索给 Agent。

| 任务 | 建议归属 | 说明 |
|---|---|---|
| IR/SR/AR 条目化起草 | AI 主责 | 人改边界 |
| 需求冲突与取舍 | 人主责 | AI 列选项 |
| AR 切分提案 | 人机共责 | AI 提案，架构确认 |
| 功能/实现设计草稿 | AI 主责 | R2 人过 |
| 时序图/类图/接口表 | AI 主责 | 人审语义 |
| UT/组件测设计与代码 | AI 主责 | R3 人过 |
| 生产代码实现 | AI 主责 | 人合入 |
| CR 意见起草 | AI 主责 | 人裁决 |
| 测试规格与用例 | AI 主责 | T1/T2 人过 |
| 自动化脚本 | AI 主责 | 人维框架 |
| HIL/实车执行判定 | 人机共责 | AI 辅助日志分析 |

| 量产/对外放行 | 人主责 | AI 汇总证据包 |

## 4. 问题二：各节点文档要求，与 IPD / 车域兼容

### 4.1 兼容策略：双轨同一真相

不要做「AI 一套 Markdown、IPD 再手抄一套 Word」。正确做法是：

> **仓库中的结构化工件是权威工作真相；IPD / 配置库中的正式文档是发布视图或签字视图，由同一数据生成或同步。**

| 传统 IPD / 车域文档 | AI 流程中的工作态工件 | 关系 |
|---|---|---|
| 原始需求 / IR | IR 包（条目 + 场景 + 约束） | 正式稿可从 IR 包导出 |
| 需求分析说明书 | SR 规格集 + IR↔SR 追溯 | 说明书 = 叙事封面 + 规格附录 |
| 功能设计说明书 | 系统/组件功能设计增量 + AR 分配表 | 设计评审仍走原会议，材料改读增量 |
| AR 实现设计说明书 | `delta-design.md`（结构、时序、错误、测试设计） | 满足原审查要素，去掉与代码重复的废话 |
| 代码与 UT | 源码 + 测试 + RED/GREEN 证据 | 仍走 CR；证据链更强 |
| 测试规格 | SR 测试规格（映射 AC） | 可导出到原测试管理工具 |
| 测试用例 / 报告 | TC + 自动化 + 执行证据包 | 报告自动生成，人签放行 |
| 问题单 | 缺陷工作项 + fix AR | 状态机与原缺陷流程对齐 |

车域额外硬约束（保持，不因 AI 减弱）：

- 安全相关变更必须引用 safety goal / ASIL，owner 确认前 blocking。
- 诊断 DTC、信号矩阵、电源/网络管理等引用整车规范章节，禁止凭记忆编写。
- 测试层级（UT / SIL / HIL / 整车）在测试策略中显式声明；mock 必须忠于整车状态模型。

### 4.2 各节点「最小必要文档」：写什么、不写什么

#### IR 包

必须有：意图、用户/整车场景、成功标准、约束（法规/安全/性能）、非目标、来源链接。  
不要写：实现方案、模块划分、类名。

#### SR 规格

必须有：可观察行为、AC（Given/When/Then）、NFR（可度量）、接口候选契约、依赖与假设、IR 追溯、Open Question。  
不要写：具体类设计、第三方库选型（除非约束本身是需求）。

#### 功能设计 + AR 分配

必须有：逻辑架构/职责、关键交互、AR 列表与边界、跨组件影响、安全/诊断相关设计输入。  
不要写：与实现设计重复的详细时序（留给 AR）。

#### AR 工作区（建议目录）

```text
specs/changes/ARXXX-<topic>/
  change.json          # 身份、门禁、风险 profile
  srs.md               # 本 AR 范围与增量需求（锚到 SR/AC）
  delta-spec.md        # 对组件规格的增量
  delta-design.md      # 对组件设计的增量 + 测试设计
  tasks.md             # 可冷读任务与 TDD 证据
  traceability.md      # SR/AC → spec → design/case → task → code/test → evidence
  reviews/             # R1/R2/R3 记录与 Resolution
  closeout.md          # DoD、债务、确认、归档摘要
```

组件长期真相：

```text
specs/spec.md    # 当前行为规格
specs/design.md  # 当前设计
specs/archive/   # 已关闭 AR
```

这与「写一本永远过时的实现设计说明书」相反：活动期看 delta，关闭后合并进 canonical，历史在 archive。

#### 测试规格 / 用例

必须有：SR 范围、AC 覆盖矩阵、环境层级、优先级、豁免与风险。  
每条 TC 绑定至少一个 AC；无 AC 的 TC 要么补需求，要么删除。

### 4.3 审查与基线怎么接 IPD 门禁

| IPD / 车域常见门禁 | AI 流程对应 |
|---|---|
| 需求评审 | G0 + G1（IR/SR） |
| 设计评审 | G2 + 各 AR 的 R2 |
| 代码合入 | R3 + CR |
| 测试就绪 / 开测 | T0/T1（策略与规格） |
| 版本验收 | T3（SR 证据包齐全） |
| 配置审计 / 追溯审计 | `traceability.md` + 导出矩阵 |

原则：**会议可以保留，材料换成门禁已通过的工件摘要；禁止用会议代替门禁记录。**

### 4.4 文档质量标准（给人和 AI 的同一把尺）

1. **可冷读**：新会话 / 新人只靠文档能继续，不依赖聊天历史。
2. **可测试**：需求条目带 AC；不能测的写成约束或上抛问题，不假装是功能需求。
3. **可追溯**：每个实现与 TC 能回到 SR/AC；每个 SR 能回到 IR。
4. **增量表达**：用 ADDED/MODIFIED/REMOVED，避免整篇替换掩盖删除。
5. **澄清不臆造**：未知写成 unknown + owner，不编造业务规则。

## 5. 问题三：知识工程如何形成飞轮

### 5.1 飞轮长什么样

```text
        ┌──────────── 检索 / 约束 ────────────┐
        ▼                                    │
   交付生产（规格→设计→代码→测试）             │
        │                                    │
        ▼                                    │
   结构化沉淀（canonical、archive、用例、缺陷根因、ADR）
        │                                    │
        ▼                                    │
   知识层更新（图谱关系 + 文档切片 + 质量规则）──┘
        │
        ▼
   下一轮更准的分解、更少的重复踩坑、更快的评审
```

没有回写，就只是「每次重新聊天」；没有门禁，回写的是垃圾，飞轮会把错误放大。

### 5.2 知识分层（不要一上来只上向量库）

| 层 | 存什么 | 谁写 | 谁读 |
|---|---|---|---|
| L0 权威工件 | IR/SR、canonical spec/design、AR archive、测试基线 | 交付流程强制写入 | Agent + 人 |
| L1 关系图谱 | IR→SR→AR→组件→接口→TC→缺陷→ECU | 从工件与代码扫描增量构建 | 影响分析、追溯、问答 |
| L2 检索切片 | 规范章节、设计说明、运行手册 | 入库管道 | RAG 辅助 |
| L3 协作记忆 | ADR、复盘、失败模式、评审常见 findings | 人确认后入库 | 规划与评审 Agent |
| L4 技能与规则 | 编码规范、车域红线、Definition of Done | 平台组维护 | 所有 Agent 强制加载 |

Harness、Bito 一类实践把知识图谱和 RAG 并用：文档切片负责广度，图谱负责影响面和关系。只有切片，Agent 做不好跨组件分析；只有图谱却没有归档纪律，图谱会漂。两者要一起做，而且 **L0 工件纪律先于 L1/L2 平台化**。

### 5.3 回写触发点（写进流程，而不是靠自觉）

| 触发点 | 回写内容 |
|---|---|
| G1 SR 冻结 | SR 节点、IR 边、AC |
| AR ship | 规格/设计 canonical、archive、接口变更、追溯终态 |
| R3 / CR 常见 findings | 「失败模式」条目（去敏后） |
| 缺陷关闭 | 根因标签、复现 TC、是否补 SR/AC |
| SR 验收 | 证据包索引、遗留风险 |
| 架构决策 | ADR（上下文、决策、后果） |

### 5.4 防漂移机制

- canonical 只有一份当前真相；AR 关闭必须 sync，不允许「代码已合、规格未合」。
- 图谱边以 ID 为键；删除用 REMOVED 语义，不做静默覆盖。
- 技能评测（evals）盯住：是否臆造需求、是否跳过上抛、是否假绿测试。
- 定期（如每迭代）抽检：随机 N 个 SR，核对 AC↔TC↔最新代码是否仍成立。

### 5.5 90 天可启动的最小知识工程

1. 选定 1～2 个组件，补齐 `spec.md` / `design.md` 基线。  
2. 新 AR 全部走变更目录与追溯，结束即归档。  
3. 用表格或轻量图谱先打通 ID 关系（不必先上图数据库）。  
4. 把车域红线、编码规范做成 Agent 必载技能。  
5. 缺陷根因每周沉淀 5 条「可检索卡片」。  

平台可以后置；**工件纪律与 ID 体系前置**。飞轮先转起来，再加检索与图谱自动化。

## 6. 问题四：交付小团体的组织设计

### 6.1 为什么要「小团体」

设计 / 开发 / 测试三团队分工适合管控与专业纵深，但 AI 提速后，最大浪费变成**等待与重新解释**。交付小团体（Squad）按 **SR 或紧密 SR 组** 拉通端到端结果，职能团队变成能力中心（Capability Center），而不是每张工单的必经审批链。

推荐结构：**实线在能力中心，虚线在交付小团体**（或反过来，按你们人事制度选一种，但责任必须唯一）。

### 6.2 一个交付小团体的角色

规模建议：核心 **5～8 人** + 共享专家。再大就拆 SR 或拆领域。

| 角色 | 人数感 | 职责 | AI 用法 |
|---|---|---|---|
| 交付负责人（DL） | 1 | SR 结果负责、优先级、放行协调、阻碍升级 | 用 AI 汇总状态与风险，不代替决策 |
| 系统工程师（SE） | 1 | IR/SR 质量、AR 切分协同、跨域接口、G0/G1/G2 | AI 起草规格；人审边界与上抛 |
| 模块工程业主（Dev Owner） | 1～2 | 组件设计真相、AR 工程交付、R2/R3/合入 | AI 实现；人守架构与合入 |
| 验证业主（QA Owner） | 1 | SR 测试策略、T0–T3、自动化质量、验收证据包 | AI 生成用例；人定策略与放行建议 |
| AI 流程工程师（AE） | 0.5～1（可共享） | Agent 技能、门禁、知识回写、评测、工具链 | 造杠杆的人，不当「提示词专员」长期客串开发 |
| 共享：功能安全 | 按需 | ASIL/安全机制确认 | 检查清单 + 人工确认 |
| 共享：架构 / 诊断 / 集成 | 按需 | 跨 ECU、信号、HIL 环境 | 影响分析辅助 |

角色可以一人兼两职（早期常见：Dev Owner 兼 AE），但 **DL、SE、验证签字** 不宜全叠在同一个人身上，否则门禁失效。

### 6.3 与职能团队的分工

| 能力中心 | 保留什么 | 交给 Squad 什么 |
|---|---|---|
| 设计 / SE 部 | 方法、复用需求资产、跨产品一致性、难点支援 | 本 SR 的需求分析与 AR 分配日常 |
| 开发部 | 编码规范、组件长期演进、平台基建、人力池 | 本 SR 相关 AR 的交付 |
| 测试部 | 测试框架、环境、质量标准、独立抽检 | 本 SR 的规格化验收与自动化 |
| AI 平台组（新建或挂工具链） | 模型接入、知识平台、技能包、安全合规 | 对 Squad 提供可运行能力与咨询 |

### 6.4 小团体运作节奏

- **迭代计划**：以 SR/AR 看板为中心，不按职能排队。  
- **每日**：门禁与阻塞可视化（blocked 必须有 owner）。  
- **AR 完成**：工程 DoD + 合入；不自动等于 SR 完成。  
- **SR 完成**：全部相关 AR 证据 + T3。  
- **复盘**：只沉淀可检索的失败模式与 ADR，不写空泛总结。

### 6.5 能力模型变化（对人的要求）

| 原岗位侧重 | 转向 |
|---|---|
| SE 写长文档 | 定义可测试契约、切 AR、审 AI 草稿、管追溯 |
| 开发写代码为主 | 设计审查、任务化解、证据化 CR、维护 canonical |
| 测试写用例为主 | 风险策略、AC 覆盖、环境与自动化资产、放行证据 |
| 全员新增 | 会读门禁、会开 Agent、会拒绝臆造、会回写知识 |

考核建议从「个人产出页数/行数」转向：**门禁一次通过率、SR 周期、逃逸缺陷、知识回写质量、返工轮次**。

### 6.6 治理：什么时候 Squad 说了算，什么时候必须上抛

Squad 内可决：本 SR 范围内的 AR 顺序、实现方案、测试用例细节、非安全缺陷优先级。  

必须上抛：安全目标与 ASIL、跨 ECU 契约、整车规范解释、公共平台接口破坏性变更、发布范围、资源承诺。

AI 不允许「默默实现上抛项」。流程里应把这类项做成 blocking Open Question。

## 7. 落地路径（按能力成熟度，不按日历口号）

### 阶段 0：对齐与选点

- 选一个中等复杂度、接口清晰、安全等级可控的 SR 做样板。  
- 盘点该链路现有文档、ID、工具断点。  
- 组建试点 Squad，明确 DL/SE/Dev/QA/AE。  
- 规定：试点 SR 必须走新门禁，不允许「AI 玩票、正式流程另走」。

### 阶段 1：工程段先打穿（AR 闭环）

- 组件基线（spec/design）补齐。  
- AR 全面使用变更工件 + R1/R2/R3 + TDD 证据 + 归档。  
- CR 模板改为消费这些证据。  
- 度量：AR 周期、R 门禁返工率、合入后缺陷。

### 阶段 2：上游 SR 与下游验收接上

- SR 规格改成可测试 AC；功能设计输出 AR 清单。  
- 测试从 AC 生成规格/用例；SR 验收吃证据包。  
- 取消或大幅缩短无工件的串讲。  
- 度量：SR 周期、AC 覆盖率、验收逃逸。

### 阶段 3：知识飞轮与规模化

- ID 图谱自动化、检索接入 Agent。  
- 低风险 profile 允许 unattended 连跑。  
- 技能与评测体系化；多 Squad 复制。  
- 能力中心转向标准与平台，减少个案审批。

每阶段出口看证据，不看「是否采购了某工具」。

## 8. 度量与风险

### 8.1 建议度量

| 类别 | 指标 | 用意 |
|---|---|---|
| 流速 | IR→SR 冻结时长、AR 周期、SR 验收周期 | 看端到端是否变快 |
| 质量 | 门禁一次通过率、合入后缺陷、验收逃逸 | 防止「更快但更烂」 |
| 协作 | 串讲次数与时长、因理解偏差导致的返工 | 看交接是否被工件替代 |
| 知识 | 归档完整率、追溯断裂数、缺陷卡片复用次数 | 看飞轮是否转 |
| AI 有效性 | AI 草稿采纳率、幻觉导致返工数、人工确认耗时 | 看人机分工是否健康 |

### 8.2 主要风险与对策

| 风险 | 对策 |
|---|---|
| AI 加快了错误传播 | 规格/设计门禁前置；作者不自审 |
| 双轨文档打架 | 单一工作真相 + 导出正式视图 |
| 安全相关被「顺手改掉」 | 车域技能红线 + 上抛 blocking |
| 测试自动化膨胀难维护 | AC 绑定、去重、不稳定用例治理 |
| Squad 与职能抢权 | 书面界定决策边界与上抛清单 |
| 知识库污染 | 只入库门禁通过后的工件；卡片需人确认 |
| 人变成「无脑点批准」 | 抽检 + 评测 + 对确认质量考核 |

## 9. 直接可执行的结论

1. **全流程打通**的关键不是更多插件，而是一条 ID 贯通的交付链：IR→SR→AR→代码/测试证据→SR 验收；串讲改为门禁评审。  
2. **人机分工**上，起草与实现默认 AI，边界、安全、架构、放行默认人；每个阶段有显式门禁。  
3. **文档**与 IPD/车域兼容的方式是「工作态结构化工件为真相，正式文档为视图」，审查要素保留，写法从叙事改为契约与增量。  
4. **知识飞轮**从 L0 工件纪律起步，再叠加图谱与检索；每次 ship / 缺陷关闭 / 复盘强制回写。  
5. **组织**上用交付小团体对 SR 结果负责，角色至少覆盖 DL、SE、Dev Owner、QA Owner，并以 AE 维护 AI 杠杆；职能团队退到标准与资源池。

若只选一件事先做：挑一条真实 SR，按本文门禁跑通「可测试 SR → 若干 AR 的规范驱动交付 → AC 证据驱动的 SR 验收」，并用追溯矩阵证明没有断链。样板跑通前，不要铺开工具采购与全员培训。

## 附录 A：与 DevFlow 工程模型的映射

| 团队传统概念 | DevFlow / 本方案概念 |
|---|---|
| AR | `specs/changes/ARXXX-<topic>/` 变更 |
| 实现设计说明书 | `delta-design.md` + 归档后的 `specs/design.md` |
| UT 用例 | 测试设计 + `tasks.md` 中 RED/GREEN 证据 |
| 代码审查 | R3 + CR |
| 组件设计长期文档 | `specs/design.md` |
| 需求分析中的可测试部分 | SR / `srs.md` + `delta-spec.md` |
| 追溯矩阵 | `traceability.md` + 系统级 IR/SR 索引 |

DevFlow 覆盖「已接受的工程工作项 → 可维护合入」；本方案把其上游（IR/SR/功能设计）与下游（SR 级验证）接到同一条链上。

## 附录 B：门禁一览（可贴到团队墙）

```text
G0 IR 准入 → G1 SR 冻结 → G2 AR 就绪
  → R1 规格 → R2 设计 → R3 测试与代码 → Ship/合入
  → T0 策略 → T1 测试规格 → T2 用例基线 → T3 SR 验收
```

任一 `blocked` 必须有人名与到期；`rework` 必须有 Resolution，禁止口头「已知晓」。
